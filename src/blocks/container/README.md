# motto/container

## Purpose

Primary layout wrapper block. Used for sections, rows, cards, column wrappers, and any structural container that groups other blocks. Renders as a configurable semantic tag with an optional background image (parallax-capable), color/gradient overlay, and a full-block link.

Accepts any inner blocks (`InnerBlocks`, no `allowedBlocks` restriction). `mottoBaseLayout` is `"flow"` (block-level display by default; Styler can override to flex/grid — see `docs/conventions/block-layout.md`).

## Attributes contract

Non-obvious fields only — see `block.json` for the full list and defaults.

- **`tagName`**: one of `div | section | article | main | header | footer | aside`. No semantic validation beyond the fixed option list.
- **Background image** — two mutually exclusive sources:
  - Static: `backgroundImageUrl` / `backgroundImageId` (+ `backgroundPosition`, `backgroundFocalPoint`, `backgroundSize`, `backgroundRepeat`, `backgroundAttachment`).
  - Dynamic (Pro-only): `backgroundDynamic` (object) — resolved through `applyFilters(BLOCKS_HOOKS.imageSourceDynamicSection, ...)`; Free renders a disabled "PRO" toggle when the filter isn't registered.
  - `backgroundImageEnabled` is a derived convenience flag, not an independent source of truth — it's recomputed from whichever source has a URL every time either source changes (see `updateBackgroundLayer` in `index.jsx`).
- **Parallax**: `backgroundParallax` (bool) + `backgroundParallaxOffset` (px, 20–400, default 120). Only meaningful when a background image source is present (`hasBackgroundSource`); the panel controls hide themselves otherwise.
- **Overlay**: `overlayEnabled` + `overlayStyle` (`color | gradient`) + `overlayColor` / `overlayGradient`. `getActiveOverlayFillType()` in `index.jsx` resolves which one actually renders when both are set (prefers `overlayStyle`, falls back to whichever is non-empty).
- **Link container**: `linkContainerUrl`/`linkContainerNewTab`/`linkContainerNoFollow` (static) or `linkDynamic` (Pro). Renders as an absolutely-positioned `<a class="motto-container__link-overlay">` sibling *after* inner blocks — nested interactive elements inside the container (buttons, links) still receive clicks because they're later in DOM order/z-index, not because of any special-cased logic.
  - **Pattern Overrides (SDD-032)**: `linkContainerUrl` is `source: "attribute"` off `.motto-container__link-overlay`'s `href`, `role: "content"`; `linkContainerNewTab`/`linkContainerNoFollow` are `role: "content"` too but with no `source` (same treatment as `mediaId` on `motto/image`, since they're booleans, not markup-derivable strings) — parity with `core/button`, which marks `url`/`linkTarget`/`rel` all `role: "content"`. `includes/container-render.php` hooks `block_bindings_supported_attributes_motto/container` (WP core's allowlist extension point, required since 6.9.0 alongside `role: "content"` — see `docs/conventions/block-layout.md`'s "Native Pattern Overrides" section) with all three attribute names. `linkContainerEnabled`/`linkDynamic` are not overridable — see Out of scope in the spec for why.
  - **One panel, two possible locations**: `edit()` computes `hasLinkOverride` from `attributes.metadata?.bindings?.__default?.source === "core/pattern-overrides"` (what "Enable overrides" sets) and renders a single "Container Link" `PanelBody` (URL + both toggles, one `MottoLinkControl` instance) either inside `<InspectorControls group="content">` (when an override is active — required for the panel to survive Gutenberg's "content only" editing mode while editing a placed synced-pattern instance) or inline in the default `<InspectorControls>` at its original position (when it's not). A normal container never using the feature sees the exact same single panel it always has; the split only appears once "Enable overrides" is actually on for that block. The Pro dynamic-link picker lives in its own separate, always-default-group "Dynamic Link" panel regardless of override state — dynamic mode isn't overridable, so it never needs to move. `MottoLinkControl` gained `dynamicOnly` (renders only the dynamic-source section/stub, nothing else) and `dynamicLabel` (overrides the stub's default `"Dynamic URL"` heading text — container passes `"Enable"`, since the panel title already says "Dynamic Link") to support pulling the picker out into its own instance; both are opt-in and don't change `motto/button`'s/`motto/svg`'s existing combined-panel behavior. When `linkDynamic` (Pro) resolves a source *and* an override is active, the "Container Link" panel body shows a `motto-section-help` note instead of the fields — the override would be inert at render time (`includes/container-render.php`'s dynamic-link filter, priority 11, always overwrites the href after the override splice at priority 10), same caveat as `motto/image`'s dynamic mode. Unlike `motto/image`'s `<img>`, the `<a class="motto-container__link-overlay">` only exists in saved markup when `linkContainerEnabled` is true and `linkContainerUrl` is non-empty — a pattern with no link set has nothing for the binding to read from.
  - **Frontend override splice is Free's own code, not WP core's** (`includes/container-render.php`, priority 10, registered before the Pro dynamic-link filter above): WP core's private `WP_Block::replace_html()` (the generic mechanism that's supposed to write a resolved binding value into markup) locates the target via `WP_HTML_Tag_Processor::next_tag(['tag_name' => $selector])`, which only matches a bare HTML tag name — never a CSS class selector like `.motto-container__link-overlay`, so it silently no-ops for `linkContainerUrl`; `linkContainerNewTab`/`linkContainerNoFollow` have no `source` at all, so `replace_html()` skips them unconditionally regardless. A bare `"a"` selector would be unsafe for the URL case too (unlike `core/image`/`core/button`, this block can contain arbitrary inner blocks with their own `<a>` tags rendered *before* the link overlay). So Free's own filter reads all three binding-resolved values from `$block_instance->attributes` (that part of core's mechanism — resolving the override's *value* — works fine regardless of `source`; only the *write-back* is broken/absent) and splices them in itself via the same class-scoped lookup `motto_blocks_apply_container_link_override()` uses for the Pro case (extended to also set/remove `target` and set `rel`, not just `href`), guarded by comparing resolved vs. pre-binding values so untouched containers are never re-processed.
- **Content width (`supports.layout: true`, SDD-021)**: `motto/container` opts into WP core's native block-supports layout mechanism — same as `core/group`. WP core auto-manages the `layout` attribute, injects its own native "Layout" inspector panel (toggle "Inner blocks use content width" + Content/Wide width overrides + Justification — WP-styled, not Motto's `motto-panels`, an accepted tradeoff), adds `is-layout-constrained`/`is-layout-flow` + a unique `wp-container-content-*` class to the root, and generates the constraining CSS from the active theme's `theme.json` `settings.layout.contentSize`/`wideSize`. `edit()` derives `usedLayout` from `attributes.layout` (fallback `{ type: "default" }`) and passes it to `useInnerBlocksProps` so nested child blocks' toolbar Wide/Full alignment options correctly gate on the parent's constrained state, matching `core/group`'s real behavior (confirmed empirically). Earlier attempts at a restrictive `supports.layout` object (`allowSwitching: false`) produced an empty panel; the bare `true` form was the one that worked. Because WP's generated constrained CSS targets *any* non-`align*` direct child, `container.scss` explicitly forces `max-width: none` on the internal `.motto-container__bg-media`/`__bg-overlay`/`__link-overlay` layers so they keep covering 100% of the container instead of being clamped like a real content child. Orthogonal to `mottoBaseLayout`: that governs the container's own `display`; this governs its children's max-width. Combining a Styler `display: flex`/`grid` container with this toggle on can produce confusing auto-margin behavior on children — same caveat `core/group` has, not fixed here.
  - **`save()` child order is load-bearing (SDD-021 v0.5)**: `<InnerBlocks.Content />` must render as the *first* child inside the root element, before `bg-media`/`bg-overlay`. WP core's `wp_render_layout_support_flag()` finds "the inner block wrapper" on the frontend by scanning the raw saved HTML for the last complete tag before the first inner block starts, and applies the constrained/layout classes (including the one carrying the actual `max-width` CSS) there. With any self-closed decorative div (`bg-media`/`bg-overlay`) before `InnerBlocks.Content`, that div — not the real content — silently absorbs the classes, so the constrained toggle visibly works in the editor (React-driven, unaffected by this heuristic) but never clamps anything on the frontend. Verified empirically on a live site. Safe to keep `InnerBlocks.Content` first because `container.scss` stacks all layers by explicit `z-index` (media 0, overlay 1, real content 2, link-overlay 3), not DOM order — don't reintroduce a decorative div before it without re-checking this.

## Behavior

- **Editor vs. frontend background rendering**: if `backgroundRepeat !== "no-repeat"` or `backgroundAttachment === "fixed"`, the background renders as a CSS `background-image` `<div>` (`containerBackgroundNeedsDivFallback()`); otherwise it renders as an `<img>` using `object-fit`/`object-position`, because CSS `object-fit` has no equivalent for tiling or fixed attachment.
- **Focal point auto-fallback (editor only)**: if the user hasn't customized `backgroundPosition`, the editor previews the source attachment's saved focus point (from the "Media Focus Point" plugin's `bg_pos_desktop` postmeta) as a live fallback. On selecting a *new* static image, that focus point is baked into `backgroundPosition`/`backgroundFocalPoint` once via `resolveSelect("core").getEntityRecord("postType", "attachment", id)` (see `updateBackgroundLayer`) — `save()` is pure and can't read attachment meta at render time, so this must happen at selection time, not render time.
- **Editor parallax preview**: `useScrollParallaxPreview` (`src/components/hooks/use-scroll-parallax-preview.js`, shared with `motto/image`) drives a live scroll-linked `translateY` on the background layer inside the editor canvas via a manual `requestAnimationFrame` loop (no external library — kept dependency-free for WordPress.org distribution), for visual feedback only.
- **Frontend parallax**: a separate, hand-authored runtime — `assets/js/parallax-runtime.js` — is registered in PHP (`motto_blocks_register_container_assets()`, `includes/assets-frontend-libs.php`) with no external dependencies. It reads the `--motto-parallax-offset` CSS custom property set inline by `getBackgroundImageStyles()` and recomputes each layer's translateY from live scroll position every animation frame (shared `window.MottoBlocksParallax` primitives, also reused by Pro's Image parallax).
- **Transforms**: any multi-block selection converts to one `motto/container` wrapping the selected blocks (keeps the widest `align` among them). `core/group`, `core/columns`, and `core/cover` convert directly, keeping only `tagName`. `ungroup` unwraps to the inner blocks.

## Implementation notes

- `getBackgroundImageStyles()` and `getOverlayStyles()` are pure functions shared between `edit` and `save` (and reused with different option flags for URL quoting / origin normalization) — keep new background/overlay fields flowing through these rather than inlining styles at either call site.
- `normalizeUploadedMediaUrlForCurrentSite()` rewrites a stored absolute `/wp-content/uploads/` URL to the current site's origin if they differ — a multisite/staging-sync safeguard for the *editor preview only* (frontend `save()` output keeps the stored URL as-is via `normalizeSiteOrigin: false`).
- Pro dynamic background/link resolution is Pro's responsibility via the `BLOCKS_HOOKS.imageSourceDynamicSection` filter and `hasDynamicImageSource`/`hasDynamicLinkSource`; this block never imports anything from `src/pro/`.
- 6 `deprecated` entries track: class renames (`motto-bg-image` → `motto-container__bg-image`, `motto-container-link-overlay` → `motto-container__link-overlay`), a removed inline `textAlign: center` default, the `<img>` vs `<div>` background rendering split being added later, and (newest, SDD-021 v0.5) `InnerBlocks.Content` moving from after `bg-media`/`bg-overlay` to before them (see the child-order note above). Changing saved markup again requires a new deprecation entry, not editing an old one.

## Known limitations

- No `allowedBlocks` restriction — any block can be nested, including another `motto/container`, with no depth guard.
- The link overlay is a single URL for the whole container; per-element links inside still need their own `motto/button` or link block (the overlay does not suppress nested link clicks, but doesn't compose with them beyond DOM order either).
- `supports.layout: true` (SDD-021) makes WP core auto-manage `attributes.layout` and its associated classnames on `save()`, which changes the serialized markup for *every* container, including ones that never touch the toggle (`is-layout-flow` now appears where no layout class existed before). Whether this trips "invalid block" validation on pre-existing content — and therefore whether a `deprecated` entry reproducing the old `save()` output is needed — was deliberately left to be verified empirically rather than assumed; check before shipping to a site with real pre-existing `motto/container` content.
- SDD-021 v0.5's child-order fix only changes `save()` going forward — it does not touch already-published content. A `motto/container` published before v0.5 keeps the old (broken) markup baked into `post_content` until someone reopens that page and re-saves it; there's no bulk-migration path for existing content.
