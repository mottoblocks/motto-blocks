# motto/maps

## Purpose

Google Maps embed block with a configurable center/zoom/map-type and a list of custom pins (icon type, color, title/description/link shown in an info window). Both editor and frontend render a live Google Maps JS instance directly into a canvas `<div>` — there is no iframe embed and no static image fallback.

No inner blocks. `mottoBaseLayout` is `"flow"`. `align` supports only `wide`/`full` (no `left`/`right`/`center`/unset, per `block.json`).

This is a dynamic block: `save()` always returns `null`; all frontend markup comes from the PHP render callback `motto_blocks_render_maps()` in `includes/helpers.php`.

## Attributes contract

Non-obvious fields only — see `block.json` for the full list and defaults.

- **`pins`**: array of `{ id, lat, lng, title, description, url, pinColor, iconType, iconValue, iconSvg }`. `iconType` is one of `none | svg-library | svg-inline | image`; `iconValue` shape depends on `iconType` (a Lucide icon slug string for `svg-library`, raw SVG markup string for `svg-inline`, `{ id, url }` for `image`). `iconSvg` is a cache: for `svg-library`, the actual fetched-and-sanitized SVG markup is baked into this field at edit time (see Behavior) so the frontend doesn't need to fetch it again.
- **`controls`**: object of four booleans (`zoomControl`, `fullscreenControl`, `streetViewControl`, `mapTypeControl`) — not individual top-level attributes.
- All numeric attributes (`height`, `centerLat`, `centerLng`, `zoom`) are re-clamped on every read, both in JS (`clamp()`/`toFiniteNumber()` in `maps-utils.js`) and again in PHP (`motto_blocks_render_maps()`), so an attribute tampered with outside the normal UI still renders within valid bounds.

## Behavior

- **Google Maps API key dependency**: both editor and frontend need a Google Maps API key, read from the `motto_blocks_google_maps_api_key` option via `motto_blocks_get_google_maps_api_key()` (`includes/helpers.php`). It's set on **Motto Blocks → Settings → API** (`includes/admin/render-tabs.php`, `motto_styler_render_api_tab()`), saved via `admin-post.php?action=motto_styler_save_api_settings` (`includes/admin/settings-api.php`), nonce-protected (`motto_styler_verify_admin_request`). The settings field always renders empty with a masked placeholder (`motto_styler_get_masked_secret_placeholder()`) showing only the last 4 characters of the saved key — submitting the form blank keeps the existing key rather than clearing it.
- **Editor access to the key is capability-gated**: the key is localized to the editor as `window.__MOTTO_BLOCKS_API_SETTINGS__.googleMapsApiKey` (`motto-blocks.php`), but only if the current user passes `current_user_can( apply_filters( 'motto_blocks_google_maps_api_key_capability', 'edit_posts' ) )`. A contributor without that capability sees the "missing key" notice in the editor even when a key is configured.
- **Missing key — editor**: `index.jsx` never mounts a map (`useMapInstance` bails out early when `!apiKey`); instead it renders `MapPreviewNotice` (`MapPreviewNotice.jsx`), a warning `Notice` linking to the settings page (`settingsApiUrl`, defaults to `/wp-admin/admin.php?page=motto-blocks-settings&tab=api`).
- **Missing key — frontend** (`motto_blocks_render_maps()` in `includes/helpers.php`): if the visitor is **not logged in**, the function returns an empty string — nothing is output at all, not even a notice, so anonymous visitors never see a broken map. If the visitor **is logged in**, it renders a `.motto-maps--missing-api` notice; the "Open API settings" link inside it is only added `if ( current_user_can( 'manage_options' ) )` — other logged-in users see the notice text but no link.
- **Editor live map**: `useMapInstance` (`use-map-instance.js`) creates a real `google.maps.Map` in the canvas ref on mount and keeps it in sync: pan/zoom is written back to `centerLat`/`centerLng`/`zoom` on the map's `idle` event, and pins render as draggable `Marker`s whose `dragend` updates the pin's `lat`/`lng`. Both attribute writes go through `applyAttributes()`, which calls `setAttributes()` **and** `updateBlockAttributes(clientId, partial)` from `core/block-editor` — the direct data-store dispatch is used alongside the normal `setAttributes` prop because the map's `idle`/`dragend` listeners are bound once at marker/map creation and only close over the dispatch functions, not fresh React props.
- **Block-editor drag conflict**: `useEditorBlockDragLock(canvasRef)` (shared hook, `src/components/hooks/use-editor-block-drag-lock.js`) strips `draggable` off the ancestor `[data-block]` wrapper while the canvas is mounted, so Gutenberg's own block-drag handling doesn't compete with dragging pin markers or panning the map.
- **`svg-library` pin icons are fetched from the plugin's own bundled copy**: when a pin's `iconValue` (a Lucide icon slug) has no cached `iconSvg` yet, `useMapInstance` fetches `{MOTTO_BLOCKS_URL}assets/vendor/lucide/icons/{slug}.svg` (base URL localized as `window.__MOTTO_BLOCKS_LUCIDE_ICON_BASE_URL__`, see `motto_blocks_register_editor_script()` in `motto-blocks.php`; the SVG files themselves are copied from the `lucide-static` npm package by `npm run icons:lucide-vendor`, scripts/copy-lucide-icons.mjs, using the same shared icon allowlist as the rest of the editor's Lucide usage), runs it through `sanitizeFetchedSvgMarkup()` (blocks `<script|iframe|object|embed|foreignObject>`, `on*=` handlers, and `javascript:`/`data:` URLs), then bakes the sanitized markup into `pin.iconSvg` so future renders don't refetch. `toMarkerIcon()` then colorizes that cached SVG per-pin via `colorizeSvgMarkup()` before encoding it as a data URI marker icon.
- **Frontend marker icons mirror the editor logic** (duplicated, not shared code — `assets/js/maps-frontend.js` reimplements `toMarkerIcon`/`colorizeSvgMarkup`/`getLucideIconUrl` standalone rather than importing from `maps-utils.js`). If a `svg-library` pin somehow reaches the frontend with no cached `iconSvg`, the frontend falls back to pointing the marker icon directly at the same local `assets/vendor/lucide/icons/` URL (localized via `motto_blocks_register_maps_assets()` in `includes/assets-frontend-libs.php`) — in that fallback path the icon is **not** colorized (no `pinColor` applied), since `colorizeSvgMarkup` needs the SVG text, not a URL.
- **Frontend info windows**: `buildInfoWindowHtml()` in `maps-frontend.js` escapes title/description via `escapeHtml()` and only renders the pin's link if `isSafeUrl()` (`/^(https?:\/\/|\/)/`) passes, blocking `javascript:`-style URLs from pin data.

## Implementation notes

- Registered in `motto-blocks.php` (`motto_blocks_register_maps_block()`) with `render_callback: 'motto_blocks_render_maps'` and `view_script_handles: ['motto-blocks-maps-view']`. The view script (`assets/js/maps-frontend.js`) is registered separately in `includes/assets-frontend-libs.php` (`motto_blocks_register_maps_assets()`) with **no dependencies** — it loads the Google Maps JS API itself via a dynamically injected `<script>` tag (`loadGoogleMaps()`), it doesn't rely on `wp_enqueue_script` deps for that.
- `assets/js/maps-frontend.js` is a hand-written vanilla-JS IIFE with no corresponding source file under `src/` in this plugin — unlike most other frontend runtimes, it isn't built from a bundler entry point, so edits must be made directly to the `assets/js/` file (same "hand-authored, not bundled" pattern as `assets/js/parallax-runtime.js` documented in the container README, but maps' runtime has no shared origin with any editor-side module — `load-google-maps.js`/`maps-utils.js` under `src/blocks/maps/` are separate, editor-only copies of similar logic).
- PHP render output embeds the API key directly in the rendered HTML (`data-api-key="..."`) so the frontend runtime can read it without an extra request — this is expected for Google Maps JS keys (they're client-side by design), and the admin settings UI itself tells the user to restrict the key by HTTP referrer in Google Cloud Console rather than relying on secrecy.
- `data-user-logged-in="1|0"` on the wrapper controls whether `maps-frontend.js` appends a visible "Google Maps could not initialize…" error message on load failure (e.g. bad key, referrer restriction) — only shown to logged-in users, mirroring the same "don't expose config errors to anonymous visitors" pattern used for the missing-key notice.
- Map interaction options (`clickableIcons: false`, `scrollwheel: false`, `disableDoubleClickZoom: true`, `keyboardShortcuts: false`) are set identically in both `use-map-instance.js` (editor) and `maps-frontend.js` (frontend) — kept in sync by convention, not by sharing code.
- `motto_blocks_normalize_maps_pins()` / `motto_blocks_normalize_maps_controls()` / `motto_blocks_normalize_maps_pin_icon_value()` (`includes/helpers.php`) re-validate and re-sanitize the stored `pins`/`controls` attributes at render time (e.g. re-running `motto_blocks_sanitize_svg()` on `iconSvg`), independent of whatever the JS-side normalizers in `maps-utils.js` already did when the attributes were saved.

## Known limitations

- No render-time fallback if the Google Maps JS API fails to load for reasons other than a missing key (e.g. network block, ad blocker) — the frontend just shows the interaction-error notice to logged-in users and a blank canvas to everyone else.
- The frontend runtime (`maps-frontend.js`) and the editor's Google Maps helpers (`load-google-maps.js`, `maps-utils.js`, `use-map-instance.js`) are independently maintained duplicates, not shared modules — a behavior fix in one does not automatically apply to the other.
- The `svg-library` picker (`MapPinIconControl.jsx`) and the local Lucide icon set (`assets/vendor/lucide/icons/`) are both scoped to a curated map-pin-relevant list (`src/blocks/maps/map-pin-lucide-icons.json`, ~49 icons — places, transport, amenities), not the full ~1864-icon set used by List/Bullets. A pin whose `iconValue` falls outside that list (e.g. from an older save, before this list existed) keeps the default marker icon rather than resolving; the `svg-inline` and `image` icon types are unaffected and can still use any icon.
