# motto/tabs

## Purpose

Outer wrapper of the Motto Tabs family: `motto/tabs` → `[motto/tab-container, motto/tab-panels]`, where `tab-container` holds one `motto/tab-button` per tab and `tab-panels` holds one `motto/tab` (content panel) per tab, matched 1:1 by a shared `tabId` string. This block owns the family's active-tab state and the mechanism that keeps buttons and panels in sync; the other four blocks' READMEs reference this file rather than re-explaining it.

`mottoBaseLayout` is `"flow"`.

## Attributes contract

- **`activeTabId`** (string, default `""`): the `tabId` of the currently active tab. Provided to every descendant via block context (`providesContext: { "motto/tabs-activeTabId": "activeTabId" }`); `tab-container`, `tab-panels`, `tab-button`, and `tab` all declare `usesContext` for it directly (WordPress context propagates through nesting without the intermediate `tab-container`/`tab-panels` blocks needing to re-provide it). This attribute is **editor-only state** — `save()` never serializes it into the frontend markup (see Behavior).
- **`syncUrlHash`** (boolean, default `false`, SDD-030): opt-in toggle, editable via a "Tabs Settings" `PanelBody` in the Inspector. Also provided to descendants via context (`"motto/tabs-syncUrlHash": "syncUrlHash"`) so `tab-button` can conditionally show its "URL slug" field. When `true`, `save()` renders `data-sync-url-hash="true"` on the `.motto-tabs` wrapper; when `false` (default), no such attribute is rendered and markup is unchanged from pre-SDD-030 output.
- **`mottoStyler`**: declared explicitly here (unlike the four child blocks, where it's injected globally via the `register_block_type_args` filter in `motto-blocks.php`).

## Behavior

- **Deliberately shallow template, real seeding done in JS (SDD-022)**: `Edit()`'s `useInnerBlocksProps` uses `template: TEMPLATE` = `[[TAB_CONTAINER_BLOCK], [TAB_PANELS_BLOCK]]` — **no nested arrays** — with `allowedBlocks: [TAB_CONTAINER_BLOCK, TAB_PANELS_BLOCK]` and `templateLock: "all"`. This is load-bearing, not an oversight: WordPress re-applies a block's `template` via `synchronizeBlocksWithTemplate()` on **every mount** whenever `templateLock === "all"` (not only on first insert — confirmed by reading `@wordpress/block-editor`'s `useInnerBlockTemplateSync`, which unconditionally sets `shouldApplyTemplate = true` for `"all"`/`"contentOnly"` regardless of whether content already exists), and that function is a plain `template.map(...)` — it recreates each `blocks[index]` when the name matches (recursing into `innerBlocksTemplate` the same way) but only ever visits as many indices as the template has, silently dropping any real block beyond that length at every depth the template specifies. A version of this TEMPLATE that gave `tab-container`/`tab-panels` a literal 2-item nested array was tried first and **reproduced empirically**: a manually-added 3rd tab survived within the same editing session but was silently deleted back down to 2 the next time the post was reopened — the exact symptom reported. Because neither `tab-container` nor `tab-panels` has any nested template entry now, `synchronizeBlocksWithTemplate`'s recursive call into their `innerBlocksTemplate` is always `undefined`, which is a documented no-op (`if (!template) return blocks;`) — so this WP-native mechanism can never see, and therefore never truncate, their actual button/panel contents, no matter how many exist.
- **Family sync (the core mechanism)**: four `useEffect` hooks in `Edit()` (`src/blocks/tabs/index.jsx`) own everything the shallow TEMPLATE above deliberately doesn't:
  0. **Default-tab seeding** — the first time both `tab-container` and `tab-panels` are completely empty (i.e. right after a fresh insert, since TEMPLATE itself creates them childless), this effect seeds 2 matched pairs itself via `replaceInnerBlocks` — `DEFAULT_TAB_SEEDS` (`tabId: "tab-1"`/`"tab-2"`, label `"Tab 1"`/`"Tab 2"`) — each button getting a real `core/paragraph` text child, each panel its usual `"Tab content…"` placeholder. This only ever fires once; once real content exists, both sides are non-empty and this branch is skipped forever, even across remounts.
  1. **ID repair** — any button or panel with a missing or duplicate `tabId` gets a fresh one via `generateTabId()`; if the tabs block is emptied entirely, `activeTabId` is cleared.
  2. **Active-id validity** — if `activeTabId` doesn't match any existing button/panel `tabId`, it's reset to the first available one.
  3. **Structural sync** — computes `desiredTabIds` as the button order plus any orphan panel-only ids, then for each id reuses the existing button/panel or auto-creates the missing counterpart (`buildTabButtonFromPanel` / `buildTabPanelFromButton`, each seeding a generic placeholder — a `core/paragraph` "Tab" for a button, the existing "Tab content…" placeholder paragraph for a panel), and calls `replaceInnerBlocks` on the `tab-container`/`tab-panels` clientIds only when the count or order actually differs from what's desired. As of SDD-022, button and panel no longer share any content attributes to copy — `tab-button`'s text/icon live in its own `InnerBlocks` (see that block's README), so orphan-repair only ever has to invent a matching `tabId` + generic placeholder content, never a copy. **Guarded** against a race with effect 1: if any button/panel currently has a missing *or duplicate* `tabId` (e.g. the render right after inserting a new button via the appender, or right after "Duplicate" clones an existing button's `tabId` too), this effect bails out for that render instead of computing `desiredTabIds` — an unrepaired empty/duplicate id would otherwise get read as "doesn't exist yet" (empty) or collapse in the `tabId → block` `Map` (duplicate), and get deleted via `replaceInnerBlocks` before effect 1's fix ever commits. Confirmed empirically for both triggers before this guard existed.
- **Editor vs. frontend active-tab state**: in the editor, `activeTabId`/context drives which `.motto-tab` is visible (`tabs.editor.scss` hides `.motto-tab:not(.is-active)`). The frontend **ignores `activeTabId` entirely** — `assets/js/tabs-frontend.js` independently defaults to the first `tab-button`'s (or first `tab`'s, if no buttons) `data-tab-id` on load, unless URL hash sync (below) picks a different one. So the front end's default-open tab is never driven by which tab was last active/selected in the editor.
- **URL hash sync (SDD-030, opt-in via `syncUrlHash`)**: when the block wrapper carries `data-sync-url-hash="true"`, `tabs-frontend.js` builds a `slug -> tabId` map from any `[data-tab-slug]` buttons (see `motto/tab-button`'s `urlSlug` attribute) and, on init, activates the tab matching `location.hash` instead of the first tab if a match exists. On every button click it still calls the existing `activate()`, and additionally — if sync is on and the clicked button has a slug — calls `history.replaceState(null, "", "#" + slug)` (not `location.hash =`, which would scroll-jump and push a history entry). Buttons without a slug never touch the URL. Slugs are fully manual (no auto-generation from the button's text, no uniqueness enforcement — same per-instance-only model as `tabId`), so two sync-enabled `motto/tabs` blocks on the same page sharing a slug will both react to the same hash; this is accepted, not treated as a bug (see SDD-030 §7).
- **Frontend runtime wiring by convention, not `viewScript`**: none of the 5 blocks declare a `viewScript` in `block.json`. Instead, `motto_blocks_build_block_registration_args()` (`includes/helpers.php`) auto-registers `assets/js/{slug}-frontend.js` / `assets/css/blocks/{slug}.css` / `{slug}.editor.css` as that block's view script/styles whenever the file exists, keyed by folder slug. The family's only such files are named for the `tabs` slug (`tabs-frontend.js`, `tabs.css`, `tabs.editor.css`), so **only `motto/tabs` gets these handles**; `tab-container`, `tab-panels`, `tab-button`, and `tab` register no assets of their own and rely on always being nested inside a rendered `motto/tabs` block (enforced by their `parent` restriction) for the shared CSS/JS to be present on the page.
- **Frontend activation** (`assets/js/tabs-frontend.js`): `initTabs()` is idempotent per `.motto-tabs` element (guarded by a `data-motto-tabs-init` dataset flag), wires a click listener per `.motto-tab-button` that activates its `data-tab-id`, and toggles both an `.is-active` class and the native `hidden` attribute on panels/buttons. The CSS rule that actually hides inactive panels is scoped to `&[data-motto-tabs-init] :where(.motto-tab:not(.is-active))` (`src/blocks/scss/tabs.scss`) — **before** the script runs (or if JS is disabled/blocked), all panels stay visible, so the block degrades to "show everything" rather than "show nothing."
- **Migration from the pre-split layout**: one `deprecated` entry (`src/blocks/tabs/index.jsx`) covers markup from before the `tab-container`/`tab-panels` split, where inner blocks were raw panels wrapped directly in a `.motto-tabs__panels` div with no buttons at all. `migrate()` assigns/repairs a `tabId` on each old panel, wraps them as `motto/tab`, and derives one `motto/tab-button` per panel via `buildTabButtonFromPanel()`.

## Implementation notes

- `generateTabId()` / `normalizeTabId()` (`src/blocks/tabs/utils.js`) are the shared ID helpers used across the whole family — `tab-button` and `tab` import them directly from `../tabs/utils`. `generateTabId()` produces `motto-tab-<8 random base36 chars>`; uniqueness is only enforced per-`tabs`-instance by the sync effect above, not globally.
- `Save()` is a thin passthrough (`useBlockProps.save` + `InnerBlocks.Content`); all family logic lives in `Edit()`, not in render output.

## Known limitations

- No ARIA tabs pattern anywhere in the family: the nav has no `role="tablist"`, buttons get `aria-selected` but no `role="tab"`/`aria-controls`, and panels get no `role="tabpanel"`/`aria-labelledby`. There is no keyboard arrow-key or roving-tabindex navigation — activation is click/tap only.
- `activeTabId` is purely editor preview state; the front end opens on the first tab by default, or on the `syncUrlHash`-matched tab if URL hash sync is enabled and the current hash matches a slug (see Behavior).
- URL hash sync has no cross-block namespacing: if two sync-enabled `motto/tabs` blocks on the same page share a `urlSlug`, both activate on a matching hash (SDD-030, deliberate — resolve by choosing distinct slugs).
- The structural-sync effect runs on every relevant render while the block is mounted, though it short-circuits via an order-string comparison before calling `replaceInnerBlocks`.
