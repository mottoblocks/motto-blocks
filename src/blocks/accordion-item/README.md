# motto/accordion-item

## Purpose

Outer wrapper for a single collapsible trigger + panel pair: `motto/accordion-item` → `[motto/accordion-trigger, motto/accordion-panel]` (SDD-024). Must live inside a `motto/accordion` — enforced both ways (`parent: ["motto/accordion"]` here, `allowedBlocks: ["motto/accordion-item"]` on the parent's `InnerBlocks`). Owns `itemId`/`isOpen` and all open-state computation; the two children own the trigger content (text + optional icon) and panel content (free-form) respectively — see their READMEs for the rendered markup. `supports.reusable` is `false`. See `../accordion/README.md` for the parent block and the shared toggle/animation mechanics.

## Attributes contract

- **`itemId`** — stable id used to build `{itemId}-trigger` / `{itemId}-panel` DOM ids (`getAccordionTriggerId()`/`getAccordionPanelId()` from `../accordion/utils.js`). Auto-filled on mount by this block's own `useEffect` if empty; also independently deduped by the *parent* accordion's effect (which can see all siblings and catches copy/paste collisions this block's own effect can't) — redundant by design, unchanged since before SDD-024.
- **`isOpen`** — persisted "open by default" state, edited via the Inspector's "Open by default" toggle. Toggling it on while the accordion's `closeOtherItems` context value is true immediately force-closes any other sibling with `isOpen: true` (via `updateBlockAttributes` on blocks found by `useAccordionContext`) — unchanged from before SDD-024.
- As of SDD-024, `label`/`customIcon`/`iconOptions`/`iconPosition` no longer exist here — trigger content moved to `motto/accordion-trigger`'s own `InnerBlocks` (text + optional `motto/svg`).

## Behavior

- **Deliberately shallow `TEMPLATE`, seeding done in JS (SDD-024, applying the SDD-022 lesson proactively)**: `TEMPLATE = [[ACCORDION_TRIGGER_BLOCK], [ACCORDION_PANEL_BLOCK]]` — no nested arrays — with `templateLock: "all"`. Per SDD-022 §4.5, `templateLock: "all"` makes WordPress re-apply a block's `template` via `synchronizeBlocksWithTemplate()` on **every mount**, and that function caps nested content at the template's literal length at any depth it specifies. Keeping both entries childless makes that recursion a permanent no-op for the trigger's/panel's real content. A `useEffect` seeds both children itself the first time this item is genuinely empty — **guarded on `directChildren.length === 0`, not "no block named trigger/panel found"** (tightened in SDD-024 §4.8 after a synthetic test showed the looser check would silently wipe real-but-unmatched children, e.g. from a `deprecated` match that didn't fully resolve, with no warning shown at all). `accordion-trigger` gets a `core/paragraph` with real text `"Accordion item"`, `accordion-panel` gets the usual `"Accordion content…"` placeholder paragraph. Fires exactly once; never re-touches real content afterward, including across remounts.
- **Duplicated `itemId`/`isOpen` kept in sync, pushed one-way from this block**: `motto/accordion-trigger` and `motto/accordion-panel` each declare their own `itemId`/`isOpen` attributes too (not just `usesContext`) — `save()` has no access to block context, so the values needed for their own `id`/`aria-*` output at save time must be real, persisted attributes on those blocks themselves. The same `useEffect` that seeds fresh children also pushes `itemId`/`isOpen` down to them via `updateBlockAttributes` whenever this block's own values change (e.g. the id-dedup effect reassigning a duplicate id, or the "Open by default" toggle). This is a **one-way, always-both-exist** sync — unlike `motto/tabs`' orphan-repair, there's no possibility of the trigger/panel pair drifting into an "only one exists" state from outside, since both are always created together by this same effect and `templateLock: "all"` prevents independent add/remove.
- **Root render**: `<div className="motto-accordion-item ...">` wrapping `InnerBlocks`/`InnerBlocks.Content` — still carries the `.is-open` class (via the shared `computeIsEditorOpen()` helper, `../accordion/utils.js`) and `data-item-id`/`data-open`, exactly as before SDD-024. This is load-bearing: `accordion.scss`'s chevron-rotation and panel-max-height rules, and `accordion-frontend.js`'s own state detection, are keyed off **this** element's class/data attributes, not anything on the trigger/panel themselves.
- **Inspector**: only the "Open by default" `ToggleControl` remains — the old "Show custom icon"/`IconPositionToggle`/`ButtonIconSelector` controls moved (conceptually) to `motto/accordion-trigger`'s own children (`core/paragraph`'s native controls, `motto/svg`'s own block), which have no Motto-owned Inspector UI of their own, mirroring `motto/tab-button` post-SDD-022.
- **`useAccordionContext(clientId)`** (private helper) — unchanged from before SDD-024: walks `getBlockParents(clientId)` to find the nearest `motto/accordion` ancestor, then `getBlocks()` on it for `siblings`, used only by the "Open by default" toggle handler's immediate mutual-exclusion enforcement.

## Implementation notes

- `computeIsEditorOpen()` (new in SDD-024, `../accordion/utils.js`) is the single source of truth for "is this item open in the editor," shared by this block, `motto/accordion-trigger`, and `motto/accordion-panel` — each reads it independently (since a single WP block can't expose two independent `InnerBlocks` regions, the three blocks can't share a single render pass) from the same inputs: `itemId`/`isOpen`/`closeOtherItems` (via attributes/block context) and `editorActiveItemId`/`editorOpenItemIds` (via the ephemeral `AccordionEditorContext`, unchanged from before SDD-024).
- Provides new block context: `motto/accordion-item-itemId`, `motto/accordion-item-isOpen` — read by `motto/accordion-trigger`/`motto/accordion-panel` for **live edit-time** reactivity (their own duplicated attributes are only refreshed by this block's push-effect, which lags by one render; context has no such lag).
- No `render.php` — fully static, `Save`-based block, same pattern as before SDD-024.
- **One `deprecated` entry (added in SDD-024 §4.8, as a same-day follow-up)**: the pre-SDD-024 shape (`label`/`customIcon`/`iconOptions`/`iconPosition` attributes, trigger/panel markup rendered inline), with a `migrate()` that builds the new `motto/accordion-trigger`/`motto/accordion-panel` children — text from the old `label` (already an HTML string, formatting like `<strong>` carries straight into `core/paragraph`'s `content`), icon from a `buildSvgAssetFromLegacyIconOptions()` helper mapping the old button-icon shape onto `motto/svg`'s `svgAsset` shape, panel content passed through untouched. Added after real published content on a live client site broke on first ship — the "unused in production" assumption this block family shipped SDD-022's sibling-spec sync work under was wrong for accordion specifically. Verified against the real affected content via a before/after text diff (0 content lost).

## Known limitations

- No `transforms` — can't convert to/from another trigger-style block, unchanged from before SDD-024.
- `supports.reusable: false` means this block can't be individually turned into a reusable/synced pattern.
- Fresh items created by `motto/accordion`'s own template (or its appender) all default to the generic trigger text `"Accordion item"` — there's no per-position distinct default text (e.g. numbered "Item 1"/"Item 2") the way `motto/tabs`' default template can seed distinct "Tab 1"/"Tab 2" text, because `motto/accordion` itself has no content-seeding effect reaching into a freshly-created item's children (only this block's own seed effect does that, generically). Confirmed acceptable per explicit user sign-off during SDD-024's design.
