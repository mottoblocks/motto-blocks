# motto/list-item

## Purpose

A single `<li>` entry of a `motto/list`. Restricted to that parent only (`parent: ["motto/list"]`) and not reusable (`supports.reusable: false`). Renders a bullet marker slot, a `RichText` text span, and (since `SDD-023`) an `InnerBlocks` slot that only accepts a nested `motto/list` sub-list. By default its bullet appearance follows the parent list's `bulletOptions` (read via block context `usesContext: ["motto/bulletOptions"]`), but each item can opt out and define its own via `overrideBullet`. `mottoBaseLayout` is `"flex"` (bullet and text sit side by side; see `list.scss`'s `align-items: flex-start; gap: var(--bullet-gap)` on `.motto-list-item`), unlike the parent list's `"flow"`.

## Attributes contract

Non-obvious fields only — see `block.json` for the full list and defaults.

- **`content`**: `type: "rich-text"`/`source: "rich-text"` bound to `.motto-list-item__text` (migrated from a plain HTML string in `SDD-023`, matching `core/list-item`'s own contract) — a single inline span, not a multi-block rich area. `edit()`/`save()` pass it to `<RichText>`/`<RichText.Content>` unchanged regardless of the underlying `RichTextData` vs. string representation.
- **`overrideBullet`** (bool, default `false`): the gate for which `bulletOptions` actually apply. `false` doesn't mean "no bulletOptions attribute" — the item still stores one (see Behavior for what happens to it).
- **`bulletOptions`**: same shape as the list's, defaulting to `type: "icon"` / `svg.lucideIcon: "star"`. Declared with a real default in `block.json`, but it is only the *effective* bullet when `overrideBullet` is true, or when parent context is unavailable — reading `block.json` alone doesn't reveal that gating.
- **No `mottoStyler`/`mottoDefaults`** declared in `block.json`, unlike most blocks (e.g. `motto/list`, `motto/container`). This does **not** mean list-item lacks Styler support: `styler-core-register-attributes` (`src/styler/runtime/register-attributes.js`) injects `mottoStyler`/`mottoDefaults` into every registered block's attributes at `registerBlockType` time by default (unless a site restricts `window.__MOTTO_STYLER_TARGET_BLOCKS__`), so list-item still gets the full Styler panel at runtime. Don't infer Styler support from `block.json` alone.

## Behavior

- **Editor sync when not overriding**: a `useEffect` in `edit()` compares `JSON.stringify(localBulletOptions)` against `JSON.stringify(parentBulletOptions)` and calls `setAttributes({ bulletOptions: parentBulletOptions })` whenever they diverge and `overrideBullet` is false. The item's *stored* `bulletOptions` attribute is therefore actively kept in lockstep with the parent, not simply ignored.
- **`save()` uses a different resolution formula than the editor converges to**: `resolvedBulletOptions = overrideBullet ? local : (hasConfiguredBullet(local) ? local : parent)` (vs. `edit()`'s plain `overrideBullet ? local : parent`). Because of the sync effect above, `local` is normally already equal to `parent` by save time, so this mostly collapses to the same result. But `hasConfiguredBullet()` treats the *untouched default* as "configured" — for `type: "icon"` it only checks `Boolean(svg.lucideIcon)`, which is true by default (`"star"`) — so if a list item's `bulletOptions` is ever persisted without the editor's sync effect having run (e.g. content written programmatically, imported, or saved before first `edit()` mount), `save()` will render that item's own unsynced default bullet instead of genuinely falling back to the parent's configured one. This is a real edge case, not just theoretical, given the default already satisfies `hasConfiguredBullet`.
- **`resolvedBulletOptions.type`** drives both a CSS class suffix (`motto-list-item--no-bullet`, `motto-list-item--default`, `motto-list-item--counter`) and the `data-resolved-bullet-type` attribute — this is what `list.scss` actually keys its per-type bullet styling off, not the raw `bulletOptions` value.
- **Bullet media rendering**: image/icon/inline-SVG markup is rendered inline by the shared `<BulletMedia>` component (`src/components/controls/bullets/bullet-media.jsx`) in both `edit()` and `save()` — nothing reads the `data-bullet-*` attributes at runtime to inject markup; those attributes (`data-bullet-type`, `data-bullet-image-url`, `data-bullet-svg-source`, `data-bullet-lucide-icon`) are only emitted as supplementary metadata alongside the already-rendered markup, and only when `overrideBullet` is true (`getLocalBulletDataAttributes()` returns `{}` otherwise — an inheriting item carries no local bullet data attributes, only `data-resolved-bullet-type`).
- `<BulletMedia>` renders nothing for `type` `"default"`, `"counter"`, or `"none"` — those three are purely CSS-driven (a `::before` dot, a CSS counter, or a collapsed zero-width slot respectively).
- **Enter/Backspace split-merge** (`SDD-023`): `RichText` wires `identifier="content"` plus the standard `onSplit`/`onReplace`/`onMerge`/`onRemove` contract (same pattern as `core/paragraph`) — Enter at a caret position splits the item's text into two `motto/list-item` blocks (the original clientId stays with the first), Backspace at the very start merges into the previous item. A newly split-off item only carries `content`; `overrideBullet`/`bulletOptions` fall back to `block.json`'s own defaults (non-override), same as `motto/list`'s `TEMPLATE`-seeded items. **Two easy-to-miss requirements, confirmed empirically** (`RichText`'s `onMerge` alone is not sufficient): (1) the block registration itself needs a top-level `merge(attributes, attributesToMerge)` function (`index.jsx`) — WP's `mergeBlocks` action checks `getBlockType(name).merge` and silently no-ops (just reselects the previous block, no data change) if it's missing, regardless of what `onMerge` does; (2) `RichText` needs `identifier="content"` or WP logs `"The RichText identifier prop does not match any attributes defined by the block."` and can't restore cursor position across the merge.
- **Nested sub-lists** (`SDD-023`): `useInnerBlocksProps` restricts children to `allowedBlocks: ["motto/list"]`, rendered after the `RichText` span inside the `<li>` (`<li>text<ul>…</ul></li>`, matching `core/list-item`'s DOM order). No default template — a sub-list only appears once inserted via the item's block appender. `motto/list`'s own `providesContext` scopes independently per nesting level, so a nested list configures its own `bulletOptions` rather than inheriting the parent's. There is no Tab/Shift+Tab keyboard shortcut to create a sub-list by indenting (unlike `core/list-item`) — the appender/inserter is the only entry point in this version.

## Implementation notes

- `hasConfiguredBullet()` and `normalizeBulletOptions()` (`bullet-options.js`) use different definitions of "has a real bullet setup" — `hasConfiguredBullet` is intentionally looser (the untouched default already counts) — and that gap is the direct cause of the `edit()`/`save()` resolution divergence described above.
- `edit()` and `save()` duplicate the `resolvedBulletOptions`/class-name/data-attribute computation almost verbatim (only the `useEffect` and the override-resolution formula differ). Any change to the bullet class/data logic must be mirrored in both; the resolution-formula difference is deliberate given the current inheritance model, not something to "simplify" away without reconsidering the underlying default-vs-parent semantics.
- Relies on `motto/list`'s `providesContext` for the shared `bulletOptions` — see `src/blocks/list/README.md` for what the parent controls (bullet defaults, per-item `padding` via `blockSelectors`) and how the context link works.

## Known limitations

- `overrideBullet` is all-or-nothing: overriding swaps the *entire* `bulletOptions` object (type + every sub-field) to local values. There's no way to inherit bullet type from the parent while overriding only one sub-field (size/color live outside `bulletOptions` as `--bullet-size`/`--bullet-color` custom properties, so those can still be tweaked independently via the Styler).
- Cannot be used outside a `motto/list` (`parent` restriction) or turned into a reusable block.
- Overriding a single item's bullet type to `"counter"` inside a non-counter list still visually numbers that item (CSS counters aren't tag-dependent), but the list keeps rendering `<ul>` since the wrapping tag is decided solely by the *list* block's own `bulletOptions.type` — a semantic tag/content mismatch in that edge case.
- No Tab/Shift+Tab indent-to-nest keyboard shortcut (`SDD-023`, deferred) — creating a nested sub-list requires the block appender/inserter inside the item, not indenting an existing sibling item.
