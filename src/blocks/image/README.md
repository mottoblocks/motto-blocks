# motto/image

## Purpose

Standalone image block: a single `<img>` with a shared media-source control (static upload/URL or Pro dynamic source), object-position control, and optional parallax. Reuses the same `ImageSourcePositionControl` used elsewhere for image+focal-point editing, and the same parallax CSS variable/class convention as `motto/container`'s background image.

No inner blocks. `mottoBaseLayout` is `"flow"`. Declares `usesContext: ["postId", "termId"]` so a Pro dynamic source can resolve relative to the post/term the block is rendered in (e.g. inside a Query Loop).

## Attributes contract

Non-obvious fields only — see `block.json` for the full list and defaults.

- **Static source** (SDD-025): flattened into top-level attributes mirroring `core/image`'s shape — `mediaId` (comment-persisted, `role: "content"`, no `source`), `url`/`alt`/`title` (`source: "attribute"` off the block's `img` element, `role: "content"`), and plain `width`/`height`/`sizeSlug`/`sizes` (no `source`, no `role`). `objectPosition` stays a separate top-level attribute (unaffected by SDD-025) and is merged back in via `normalizeImageSourcePositionValue()` at both edit and save time. `edit()`/`save()` build/read a synthetic `{ id: mediaId, url, alt, title, width, height, sizeSlug, sizes, position: objectPosition }` object locally as the adapter into the shared `ImageSourcePositionControl`/`normalizeMediaSelection` (`@components/controls/image/ImageSourceControl.jsx`), whose own `id`-keyed contract wasn't changed.
- **Pattern Overrides**: the `role: "content"` markup-derived fields above (`mediaId`/`url`/`alt`/`title`) are what makes Gutenberg's native "Enable overrides" available on this block inside a synced pattern, at parity with `core/image` — same mechanism, no custom UI. Only covers the same fields `core/image` exposes; `objectPosition`, `imageParallax*`, `imageDynamic` are not overridable. `role: "content"` alone isn't enough, though: WP core (since 6.9.0) also hardcodes an eligible-block-types allowlist in `get_block_bindings_supported_attributes()` (`wp-includes/block-bindings.php`), gating both the "Enable overrides" control and the bindings' render-time resolution. `includes/image-render.php` hooks the `block_bindings_supported_attributes_motto/image` filter (core's own extension point) to add `motto/image` to that allowlist — without it, the flat/`role:"content"` schema alone is inert. Full recipe (generalized for other blocks): `docs/conventions/block-layout.md`'s "Native Pattern Overrides" section.
- **`selector: "img"`, not a class (v0.6 fix)**: `url`/`alt`/`title` originally used `.motto-image__media` (a CSS class) as their `selector`. That works fine for the *editor*-side JS attribute-source parser (`hpq` supports real CSS selectors), but WP core's private render-time write-back (`WP_Block::replace_html()`) locates the target via `WP_HTML_Tag_Processor::next_tag(['tag_name' => $selector])`, which only ever matches a bare HTML tag name — so an active Pattern Override changed the value correctly in the editor but never reached the frontend, silently. Real `core/image`/`core/button` both use bare-tag selectors (`img`/`a`) for exactly this reason. Since this block's saved markup is always exactly one `<img>` with no nested inner blocks (unlike `motto/container`'s link overlay, which needed its own Free-owned PHP splice filter to safely avoid an ambiguous match), a bare `img` selector is unambiguous here and needs no custom PHP filter — changing it was the entire fix.
- **One conditional "Image Source" panel, not a permanent split (v0.7)**: `edit()` computes `hasImageOverride` from `attributes.metadata?.bindings?.__default?.source === "core/pattern-overrides"` (what "Enable overrides" sets) and renders a single "Image Source" `PanelBody` (`staticImageSection`) either inside `<InspectorControls group="content">` (when an override is active — required for the panel to survive Gutenberg's "content only" editing mode while editing a placed synced-pattern instance) or inline in the default `<InspectorControls>` in its usual spot (when it's not). A normal image never using the feature sees the exact same single panel it always has; the earlier design (v0.5) rendered two permanently duplicate panels — both titled "Image" — regardless of override state, which read as a confusing empty-looking duplicate (the same problem found and fixed for `motto/container`'s "Container Link" panel, SDD-032 v0.4). `imageDynamic`/`imageParallax*` aren't overridable per-instance (they belong to the pattern's shared definition), so they now live in their own two separate always-default-group panels, "Dynamic Image" and "Parallax" — split apart rather than sharing one panel, matching `motto/container`'s "Dynamic Link" precedent. Each Pro-gated stub's inner heading reads "Enable" instead of repeating "Dynamic source"/"Parallax" (the panel title already supplies that context), keeping its "PRO" badge.
- **Dynamic mode + overrides don't mix**: the "Enable overrides" toggle can't be conditionally hidden per instance (no extension point for that — see the conventions doc above), so it still appears even when `imageDynamic` is active. But `imageDynamic`'s resolution always wins at render time (`includes/image-render.php`'s `render_block_motto/image` filter overwrites whatever the override set), so an override is silently inert on a dynamic-only image. The "Image Source" panel shows a `motto-section-help` note explaining this instead of the normal picker when `imageDynamic` is active.
- **Pre-SDD-025 content**: a `deprecated` entry + `migrate()` in `index.jsx` converts the old nested `image` object (still readable from the block comment at migration time, before validation against the new flat schema) into the flat attributes above — recovers `mediaId`/`width`/`height`/`sizeSlug`/`sizes`, which have no markup-derived source and would otherwise be lost.
- **`imageDynamic`** (Pro-only): resolved through `applyFilters(BLOCKS_HOOKS.imageSourceDynamicSection, ...)`; Free renders a disabled "PRO" toggle when the filter isn't registered. `hasDynamicImageSource()` / `hasImageSource()` (`@components/hooks/dynamic-image/dynamic-image-utils`) decide whether a dynamic source counts as "set" (e.g. `mode === "field"` requires a non-empty `fieldKey`).
- **`imageParallax`** / **`imageParallaxOffset`** (px, 20–400, default 120): same semantics as container's `backgroundParallax*`, but the panel UI itself is Pro-gated — see Behavior.

## Behavior

- **Rendering is always `<img>`, never a background `<div>`** — unlike `motto/container`, which switches between an `<img>` and a CSS `background-image` `<div>` depending on repeat/attachment settings (`containerBackgroundNeedsDivFallback()`). `motto/image` has no such branch in either `edit` or `save`; there's nothing to tile or fix-attach, so `object-fit`/`object-position` on a real `<img>` is always sufficient.
- **Editor dynamic preview**: `useDynamicImagePreview(attributes.imageDynamic, context)` (`@components/hooks/dynamic-image/use-dynamic-image-preview`) fetches a preview URL from the Pro REST endpoint `/motto-blocks-pro/v1/dynamic-image-preview`, keyed by `context.postId`/`context.termId`, throttled to 4 concurrent requests via `createConcurrentRequestLimit(4)` (coalesces the burst from a Query Loop full of image blocks). `displayUrl` prefers this preview over the static `image.url`.
- **Parallax panel is Pro-gated** (differs from container): `imageParallaxSection` is only ever rendered via `applyFilters(BLOCKS_HOOKS.imageParallaxSection, null, { enabled, offset, mediaRef, onChange })`; Free's `index.jsx` never calls `useScrollParallaxPreview` itself and shows a disabled "PRO" toggle when the filter isn't registered (same pattern as the dynamic-source gate). `mediaRef` (pointing at the `<img>`) is passed through so Pro's implementation can drive the live editor preview against it. See `src/blocks/container/README.md` for how the shared hook and the `--motto-parallax-offset` custom property / `assets/js/parallax-runtime.js` frontend runtime actually work — the mechanism itself is identical, only who wires it up differs.
- **Frontend parallax class/variable**: regardless of who renders the panel, both `edit` and `save` apply the `is-parallax` class and `--motto-parallax-offset` inline style via the shared `getParallaxOffsetStyle()` helper whenever `imageParallax` is true and a source is present — this is what `parallax-runtime.js` picks up on the frontend, exactly as documented for container.
- **No-source states differ by mode**: with a static source and nothing selected yet, the editor shows `MediaPlaceholder`. With dynamic mode enabled but nothing resolved, it shows a placeholder `<ImageIcon>` in a `.motto-image__dynamic-placeholder` div instead (no upload affordance, since there's nothing to upload).

## Transforms

- **From `core/image`**: registered via `transforms.from` in `index.jsx` (shows as a "Transform to Motto Image" option on the core block). Maps `id`→`mediaId`, `url`/`alt`/`title`/`width`/`height`/`sizeSlug` straight across, and `focalPoint` into `objectPosition` via `mapFocalPointToPosition()` (`@components`). `sizes` starts empty — the size list only repopulates once the user reselects media through this block's own picker. Core-only fields with no Motto equivalent (`caption`, `href`/`linkDestination`, `lightbox`, `aspectRatio`, `scale`) are dropped, not migrated.

## Implementation notes

- `getImageDimensionsAttributes()` only forwards `width`/`height` to the `<img>` tag when both are finite and `> 0`; otherwise they're omitted (`undefined`) rather than emitting `width="0"`.
- `getParallaxOffsetStyle()` and the `PARALLAX_CLASS_NAME`/offset clamping constants are duplicated locally in this file rather than imported from container — the two blocks don't share a module for this, only the convention (CSS var name + class name) that `parallax-runtime.js` expects.
- `save()` only renders the `<img>` when `url` is set; if `hasDynamicSource` is true but `url` is empty (dynamic-only, no static fallback picked), `save()` still returns the wrapper `<div>` (so the block isn't stripped from `post_content`) but with no `<img>` inside. This block has no PHP `render_callback` in this repo (`motto_blocks_register_block( 'image' )` is called with no extra args in `motto-blocks.php`), so resolving that empty case on the frontend is entirely Pro's responsibility via code not present in this plugin.
- Pro dynamic source/parallax resolution is reached only through `BLOCKS_HOOKS.imageSourceDynamicSection` / `BLOCKS_HOOKS.imageParallaxSection`; this block never imports anything from `src/pro/`.

## Known limitations

- A dynamic-only image (no static `image` set) renders empty on the frontend if Pro isn't active to fill in the gap — see the `save()` note above.
- No `focalPoint` fallback to attachment postmeta like container's "Media Focus Point" auto-fallback; `objectPosition` defaults to `"center center"` with no live suggestion from the selected attachment's saved focus point.
