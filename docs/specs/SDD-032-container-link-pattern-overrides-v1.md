# Feature Spec: SDD-032
Version: 0.5
Status: Proposed
Owner: Blocks
Last Updated: 2026-09-23

## 1. Goal
Make `motto/container`'s link identity — `linkContainerUrl`, `linkContainerNewTab`, `linkContainerNoFollow` — support native Gutenberg Pattern Overrides, the same "Enable overrides" / edit-in-place capability `core/button` already has on its own `url`/`linkTarget`/`rel` attributes, so a pattern containing a linked `motto/container` can have its destination (URL, new-tab, no-follow) replaced per-instance without detaching the pattern. (v0.1–v0.3 scoped this to `linkContainerUrl` only; v0.4 widened it to match `core/button`'s actual precedent — see Change Log.)

## 2. Scope
In scope:
- Mark `linkContainerUrl` (`src/blocks/container/block.json`) as markup-derived, instance-specific content: add `source: "attribute"`, `selector: ".motto-container__link-overlay"`, `attribute: "href"`, `role: "content"` — mirroring `core/button`'s `url` attribute (`wp-includes/blocks/button/block.json`), which is the closest core precedent (an `href` on an anchor, not an `<img src>`).
- A `deprecated` entry + `migrate()` in `container/index.jsx` reproducing the current attribute definition (plain `linkContainerUrl` string, no `source`) and current `save()` output, so pre-existing posts/patterns load without a validation/recovery notice. Markup shape is unchanged, so `migrate()` only needs to carry the value through unchanged (see §4.2 — confirm during implementation whether a `deprecated` entry is even needed, since a `source: "attribute"` addition with unchanged save() output is typically markup-compatible; SDD-025 needed one because it also restructured the attribute *shape*, which this change does not).
- Opt `motto/container` into WP's block-bindings allowlist: extend `includes/container-render.php` with a `block_bindings_supported_attributes_motto/container` filter adding `linkContainerUrl` — same recipe as `includes/image-render.php`'s existing `block_bindings_supported_attributes_motto/image` filter (SDD-025 §7 v0.3, documented generically in `docs/conventions/block-layout.md:95-103`).
- Move the "Container Link" URL field into its own `<InspectorControls group="content">` panel in `container/index.jsx`, split from the "Container Link" `PanelBody`'s other fields (new-tab/no-follow toggles, dynamic-link Pro control) which stay in the default (non-content) group — mirroring `motto/image`'s v0.5 split between `staticImageSection` (content group) and `imageDynamic`/`imageParallax*` (default group).
- `mottoAI.description` in `block.json` and `container/README.md`'s attributes-contract section updated to describe `linkContainerUrl`'s new shape and Pattern Overrides support.

- Mark `linkContainerNewTab`/`linkContainerNoFollow` `role: "content"` too, **without** a `source` (same treatment as `mediaId` on `motto/image`, SDD-025) — they stay comment-persisted booleans; WP resolves their override value the same way regardless of `source` (`WP_Block::process_block_bindings()` doesn't require it), only the automatic HTML write-back does, and that's not applicable to a boolean anyway (see §4.1 for why converting them to string mirrors of `target`/`rel`, `core/button`'s literal approach, was rejected). Free writes the resolved values into `target`/`rel` itself, in the same filter that already handles `linkContainerUrl` (§4.3).
- Redesign the Inspector panel structure around whether an override is actually active for this block instance (`attributes.metadata.bindings`), not a fixed content/settings split: a single "Container Link" panel (URL + both toggles) that lives in `group="content"` when overrides are on, and in the default group — in its original position — when they're not. This means the vast majority of containers (no pattern involvement) see the exact same single panel they always did; the split panel only appears for containers that actually use the feature.
- Give `MottoLinkControl` a `dynamicOnly` render mode and a `dynamicLabel` override, so the Pro dynamic-link picker can live in its own always-present "Dynamic Link" panel, entirely separate from the URL/toggles panel above (dynamic mode is Out of scope for overriding — see below).

Out of scope:
- `linkContainerEnabled` becoming overridable — it's not markup-derivable (a gate on whether the `<a>` exists at all, not a value read from it); making it overridable would mean turning a link on/off per pattern instance, which core's own `role: "content"` mechanism has no precedent for (not even `core/button`, which is always a link).
- Any change to `motto/image`'s Pattern Overrides support (SDD-025, already shipped) — including `imageParallax`/`imageParallaxOffset`, which stay non-overridable by the same content-vs-design-and-behavior reasoning this spec's v0.4 discussion applied to container (a motion/behavior setting, not "what is being shown").
- Building custom override UI — same as SDD-025, Gutenberg's native "Enable overrides" entry point activates automatically once the block type has an allowlisted `role: "content"` attribute.
- `linkDynamic` (Pro) becoming overridable, or changing how `render_block_motto/container`'s existing dynamic-link filter (`includes/container-render.php`, from SDD-031) resolves at render time — it's a data-source config, not a simple content value, and its resolution already takes precedence over any override by design (§4.4).

## 3. Current Behavior
`motto/container` (`src/blocks/container/block.json`) stores its link as four plain (no `source`, no `role`) top-level attributes: `linkContainerEnabled` (boolean), `linkContainerUrl` (string), `linkContainerNewTab` (boolean), `linkContainerNoFollow` (boolean) — all comment-persisted. `container/index.jsx` edits them via `MottoLinkControl` inside a `PanelBody` titled "Container Link" (`container/index.jsx:608-629`), rendered in the block's default (ungrouped) `InspectorControls`.

When `linkContainerUrl` is set, `save()` renders `<a class="motto-container__link-overlay" href={linkContainerUrl} ...>` as an overlay element inside the container (`container/index.jsx:740-1048`, one variant per layout branch); when it is empty, no `<a class="motto-container__link-overlay">` element exists in the saved markup at all — the link overlay is conditional, unlike `core/button`'s anchor (always present) or `core/image`'s `<img>` (present whenever there's a static `url`).

Server-side, `includes/container-render.php:279-310` already has a `render_block_motto/container` filter (`motto_blocks_apply_container_link_override`, from SDD-031) that splices a Pro-resolved `linkDynamic` URL into the saved `<a class="motto-container__link-overlay">` markup at render time. No `block_bindings_supported_attributes_motto/container` filter exists yet, so even if `linkContainerUrl` were marked `role: "content"`, WP's native override UI would not appear (same gap SDD-025 §7 v0.3 found and fixed for `motto/image`).

## 4. Target Behavior

### 4.1 Attribute schema (`container/block.json`)
`linkContainerUrl` gains `source: "attribute"`, `selector: ".motto-container__link-overlay"`, `attribute: "href"`, `role: "content"`. `linkContainerNewTab`/`linkContainerNoFollow` gain `role: "content"` only (no `source` — they stay `type: "boolean"`, comment-persisted). `linkContainerEnabled`/`linkDynamic` stay fully unchanged.

Converting `linkContainerNewTab`/`linkContainerNoFollow` to string mirrors of `target`/`rel` (literally matching `core/button`'s `linkTarget`/`rel`, which are `type: "string"` holding the raw attribute value) was considered and rejected: it would be a breaking attribute-shape change requiring a migration, for two fields that are internal implementation details (`target="_blank"` vs. a boolean flag) rather than anything a pattern author needs to see as a string. `role: "content"` without `source` is valid and already has a precedent in this codebase (`mediaId` on `motto/image`) — WP's bindings *resolution* (`WP_Block::process_block_bindings()`) doesn't require a `source` at all, only the automatic HTML *write-back* (`WP_Block::replace_html()`) does, and that mechanism isn't applicable to a boolean regardless of `source` (there's no generic way to turn `true`/`false` into `target="_blank"` from a schema alone). Free performs that write-back itself either way, in the same filter already needed to work around the `.motto-container__link-overlay` class-selector gap for the URL (§7).

### 4.2 Deprecation / migration
No `deprecated` entry was added in v0.2's implementation: adding `source`/`role` to an attribute whose value was previously comment-persisted only changes *how* WP reads the attribute back (from markup vs. from the comment), not the markup itself — `save()` output is unchanged, and every pre-existing container with a link already has the same value sitting in its `<a href>` that the binding will now read from instead of the comment. This differs from SDD-025, which needed a `deprecated` entry because it restructured the attribute *shape* (nested `image` object → flat attributes) — this change keeps the same flat `linkContainerUrl` string, only its `source` changes. **Not yet empirically verified against a real pre-change post/pattern** — Acceptance Criteria's second item covers this; if live testing surfaces a validation/recovery notice, add a `deprecated` entry with the current (no-`source`) attribute definition and a `migrate()` that is a no-op passthrough for `linkContainerUrl`.

### 4.3 Read/write call sites (`container/index.jsx`)
- No change to how `linkContainerUrl`/`linkContainerNewTab`/`linkContainerNoFollow` are read or written — `MottoLinkControl`'s `url`/`onUrlChange`/`opensInNewTab`/`onOpensInNewTabChange`/`noFollow`/`onNoFollowChange` props keep calling `setAttributes(...)` exactly as before. The attributes' *storage* mechanism changes for `linkContainerUrl` only (comment → markup-derived); the two booleans keep the same storage, just gain override eligibility.
- `save()`'s per-layout-branch `<a class="motto-container__link-overlay" href={...} target={...} rel={...}>` rendering is unchanged — this markup is exactly what the new bindings read from/get spliced into.
- **v0.4 (current) design** — one `hasLinkOverride` check drives everything: `attributes.metadata?.bindings?.__default?.source === "core/pattern-overrides"` (or the same check on `linkContainerUrl` specifically, for a per-attribute binding rather than the block-wide `__default` "Enable overrides" sets). A single `containerLinkPanel` (`PanelBody` titled "Container Link", holding URL + both toggles via one `MottoLinkControl` instance) is rendered either inside `<InspectorControls group="content">` (when `hasLinkOverride`) or inline in the default `<InspectorControls>` in its original position (when not) — never both, so there's exactly one "Container Link" panel visible at any time, not a permanent duplicate. This superseded the v0.2/v0.3 design (URL always in a separate content-group panel, toggles always in a separate default-group panel) after live testing showed it read as a confusing, permanently-duplicated panel for the vast majority of containers that never use the feature.
- `MottoLinkControl`'s `hideUrl`/`hideToggles` props (added in v0.2/v0.3 for the old always-split design) were removed as dead code once the panel became unified; the component instead gained `dynamicOnly` (renders only the dynamic-source section/stub, nothing else) and `dynamicLabel` (overrides the stub's heading text, default unchanged at `"Dynamic URL"`) to support pulling the Pro dynamic-link picker into its own separate "Dynamic Link" panel (§4.1, §2). Both are opt-in and default to preserving `motto/button`'s/`motto/svg`'s existing combined-panel behavior unchanged.
- The "Container Link" `MottoLinkControl` instance still receives `dynamic={attributes.linkDynamic}` (but no `onDynamicChange`) purely so its pre-existing, override-unrelated `hideUrl={isDynamic}` behavior (hide the URL input while a dynamic source is live) keeps working now that the dynamic picker itself moved to a different panel instance.

### 4.4 Dynamic mode interaction
When `linkDynamic` resolves a URL (Pro), `render_block_motto/container`'s existing filter (`includes/container-render.php`, priority 11) overwrites the `<a href>` at render time, running *after* the new Pattern Overrides splice filter (priority 10, §7) — same "dynamic always wins" behavior as `motto/image`'s `imageDynamic` handling in SDD-025 §4.4. No schema change needed for this case. Per SDD-025's resolved risk (§7 v0.4), the native override toggle cannot be conditionally suppressed per instance — when `hasLinkOverride && isLinkDynamic` (§4.3), the "Container Link" panel body shows a `motto-section-help` note instead of the URL/toggle fields, explaining the override is a no-op while dynamic mode is active (mirrors `staticImageSection`'s note in `motto/image`). Outside of an active override, `linkDynamic` being on just hides the URL input as it always did (via `MottoLinkControl`'s pre-existing `hideUrl={isDynamic}`), unrelated to this feature.

### 4.5 Panel naming
Per the `motto-visual-system` skill's `references/panel-structure.md` (softened in this same session — see below): "Container Link" (not the shorter "Link") and "Dynamic Link" (not "Dynamic") were chosen deliberately over the shortest possible nouns, because the two panels need to read as a related, recognizable pair regardless of which Inspector tab either currently renders in. This is also why the skill's naming rule — previously a hard "short nouns, no suffixes" rule — was loosened to a suggestion: it didn't anticipate a case where two panels are genuinely one conceptual unit split by tab state, and forcing bare nouns there actively hurt clarity instead of helping it. The Pro dynamic-picker stub's default heading text (`"Dynamic URL"`, used by `motto/button`/`motto/svg`) is overridden to `"Enable"` for container's "Dynamic Link" panel via the new `dynamicLabel` prop, since the panel title already supplies the "Dynamic Link" context the default text would otherwise redundantly repeat.

## 5. Data Contract
- Inputs: `MottoLinkControl`'s `url`/`onUrlChange`/`opensInNewTab`/`onOpensInNewTabChange`/`noFollow`/`onNoFollowChange` props, unchanged; new `dynamicOnly`/`dynamicLabel` props for the separated Dynamic Link panel.
- Persistence:
  - `linkContainerUrl: string` (default `""`), `source: "attribute"` off `.motto-container__link-overlay`, `attribute: "href"`, `role: "content"`.
  - `linkContainerNewTab: boolean` / `linkContainerNoFollow: boolean` (default `false`), `role: "content"`, no `source` — comment-persisted.
  - `linkContainerEnabled`, `linkDynamic` — unchanged, plain, no `source`, no `role`.
  - No `deprecated` entry shipped (§4.2) — pending empirical confirmation this holds for real pre-change content.
- Outputs: `<a class="motto-container__link-overlay" href target rel>` markup unchanged in shape for any non-dynamic, enabled link. Gutenberg's native "Enable overrides" option becomes available on `motto/container` once its three link attributes are `role: "content"` and allowlisted via the PHP filter — but only meaningfully offers something to override when the pattern's own definition already has `linkContainerEnabled: true` and a non-empty `linkContainerUrl` (i.e. the `<a class="motto-container__link-overlay">` element actually exists in the pattern's saved markup). When an override is active, the "Container Link" Inspector panel itself relocates to the Content tab; otherwise it's an unchanged single panel in Settings.

## 6. Acceptance Criteria
- [ ] Fresh insert: setting/changing/clearing the container link, new-tab, and no-follow via the Inspector works identically to pre-change behavior — a normal (non-pattern) container shows exactly one "Container Link" panel in Settings, unchanged from before this feature existed.
- [ ] A real pre-change post/pattern containing a linked `motto/container` loads with no "block contains unexpected or invalid content" / recovery notice; Inspector fields (URL, new tab, no-follow) reflect the original values.
- [ ] A pattern containing a `motto/container` with `linkContainerEnabled: true` and a non-empty `linkContainerUrl` shows "Enable overrides" in the block's Options menu; enabling it moves the "Container Link" panel to the Content tab, and inserting the pattern into a post allows replacing that instance's URL/new-tab/no-follow in place, without detaching from the pattern — verified side-by-side against `core/button` in the same pattern.
- [ ] A pattern containing a `motto/container` with no link set (`linkContainerEnabled: false` / empty `linkContainerUrl`) does not offer a broken or misleading "Enable overrides" affordance for the link (confirm actual behavior — likely no override surface appears since there's no `<a class="motto-container__link-overlay">` in markup to bind to).
- [ ] Frontend and editor `<a class="motto-container__link-overlay">` markup (`href`/`target`/`rel`/class) is byte-identical to pre-change output for any non-dynamic link — `save()` is unchanged, only the attributes' read/write path changes.
- [ ] An active override that changes new-tab or no-follow (not just the URL) is correctly reflected on the frontend `<a>`'s `target`/`rel` — exercises the write-back logic in `includes/container-render.php`'s priority-10 filter (§7), not just WP's own (broken, for this selector) substitution.
- [ ] Pro dynamic-link (`linkDynamic`) behavior is unaffected; when an override is active and dynamic mode is on, the "Container Link" panel shows a `motto-section-help` note instead of the fields, explaining the override is a no-op while dynamic mode is active.
- [ ] The "Container Link" panel is visible and editable (URL + both toggles) while editing the block as a synced-pattern instance (content-only editing mode) — requires it to actually be rendered via `group="content"` in that state (§4.3).
- [ ] The "Dynamic Link" panel (Pro picker or "Enable" stub) is unaffected by override state — always present, always in Settings, never duplicated.
- [ ] `npm run lint` and `node scripts/validate-import-boundaries.mjs` pass with no new cross-boundary imports.
- [ ] `container/README.md`'s attributes-contract section is updated to describe the three `role: "content"` link attributes and the conditional panel behavior.

## 7. Risks and Mitigations
- Risk: unlike `motto/image`'s `<img>` (present in markup whenever there's a static `url`), `motto/container`'s `<a class="motto-container__link-overlay">` only exists in saved markup when `linkContainerEnabled` is true and `linkContainerUrl` is non-empty. A pattern authored with the link disabled has no anchor for `source: "attribute"` to bind to, so "Enable overrides" may not have anything meaningful to expose, or WP may still show the toggle with an empty/non-functional override.
  - Mitigation: verify actual WP behavior empirically during implementation (same "found during implementation, not anticipated at v0.1" pattern SDD-025 hit three times) rather than assuming; document the real behavior in the Change Log. If WP shows a broken affordance for the disabled-link case, evaluate whether a `motto-section-help` note (same device used for the dynamic-mode case) is enough, or whether it needs its own follow-up.
- Risk: `MottoLinkControl` is a shared component (also used by `motto/button` and `motto/svg`); reshaping its rendering to support container's split could require a prop-level change to the shared component that ripples into other consumers.
  - Resolved (v0.2, revised v0.4): v0.2/v0.3 added `hideUrl`/`hideToggles` to support an always-split design; v0.4's redesign (single conditional panel + a fully separate Dynamic Link panel) made those two props dead code, so they were removed, and `dynamicOnly`/`dynamicLabel` were added instead (both opt-in, default to `false`/`"Dynamic URL"` — `motto/button`'s and `motto/svg`'s combined-panel usage is byte-identical to before). No other consumer needed touching at either point.
- Risk (found v0.3, still applies to the extended v0.4 scope): WP core's own render-time block-bindings substitution (`WP_Block::replace_html()`) can't apply to `linkContainerNewTab`/`linkContainerNoFollow` at all — not just because of the class-selector issue that also affects `linkContainerUrl` (§7 v0.3), but because they have no `source` in the first place (§4.1), so `replace_html()`'s own guard (`if (!isset($block_type->attributes[$attribute_name]['source'])) return $block_content;`) skips them unconditionally. Free's own splice filter is the *only* mechanism that ever writes their resolved override values into `target`/`rel` — there's no WP fallback to lean on if Free's filter has a bug.
  - Mitigation: Acceptance Criteria's new-tab/no-follow-specific item exercises this directly; `motto_blocks_apply_container_link_override()` was extended (not duplicated) to set/remove `target` and set `rel` on the same `WP_HTML_Tag_Processor` pass that already handles `href`, keeping one code path responsible for all three.
- Risk: whether a `deprecated` entry is actually required (§4.2) is unconfirmed — guessing wrong either adds unnecessary migration code or ships a real validation break for existing content.
  - Mitigation (decision made, not yet empirically verified): v0.2 shipped without a `deprecated` entry, reasoned from the fact that `save()` output and attribute shape are both unchanged — only the attribute's read source changes, and old markup already contains the value the binding will read. Still needs a live test against a real pre-change `motto/container` fixture with a link set (Acceptance Criteria item 2) before this can be considered closed.
- Risk: the block-bindings allowlist filter and `role: "content"` marking are necessary but not sufficient (per `block-layout.md`'s documented three-part recipe) — the "Container Link" panel has to actually render via `group="content"` while `hasLinkOverride` is true, or the override UI may appear to work in the pattern's own definition but be uneditable once an instance is placed in a post (SDD-025 §7 v0.4's exact finding for `motto/image`).
  - Mitigation: explicitly test editing the link field while the block is in "content only" mode (inside a placed pattern instance, not the pattern's own editor), not just in the pattern definition.
- Risk (v0.4, new): `hasLinkOverride`'s detection (`attributes.metadata?.bindings?.__default?.source === "core/pattern-overrides"`) assumes "Enable overrides" always sets `__default` for this block type, since `motto/container` only has link-identity attributes bound — never a per-attribute `linkContainerUrl` binding on its own. Not yet empirically confirmed against a live "Enable overrides" click.
  - Mitigation: the check also covers a direct `linkContainerUrl` binding as a fallback (in case a future WP version or a manually-authored binding sets it that way instead of via `__default`); Acceptance Criteria's third item exercises the real toggle end-to-end.

Shipped without a `deprecated`/`migrate()` entry, reasoned (not yet empirically verified) from `save()` output and attribute shape both being unchanged. `container/README.md` updated. `npm run lint`, `node scripts/validate-import-boundaries.mjs`, and `npm run build` all pass. Phase C (live browser verification: "Enable overrides" appearing/functioning, pre-change fixture validation, disabled-link-case behavior, content-only-mode editing) not yet done — no browser/editor access from the implementing session, same limitation SDD-025 v0.2 had at the equivalent stage.
- v0.3: First real-browser test (by the user) surfaced two problems, both fixed:
  1. **Frontend override was silently inert.** Root cause found by reading the actual installed WP core (`wp-includes/class-wp-block.php`, WP 7.0.1): WP's own render-time block-bindings substitution (private `WP_Block::replace_html()`, `source: "attribute"` case) locates the target element via `WP_HTML_Tag_Processor::next_tag(['tag_name' => $selector])` — `tag_name` only matches a bare HTML tag name, never a CSS class selector. `linkContainerUrl`'s `selector` (`.motto-container__link-overlay`) is a class selector — required for the *editor*-side (JS `hpq`-based) attribute parser, which does support real CSS selectors, but exactly the reason core's PHP-side substitution silently no-ops for it (confirmed against real core `block.json`: `core/image`'s `url`/`core/button`'s `url` both use bare-tag-name selectors — `img`/`a` — not classes, because their content elements are the block's *entire* output). A bare `"a"` selector isn't a safe fix either, since `motto/container` can hold arbitrary inner blocks that may render their own `<a>` tags *before* the link overlay (always the last sibling) — `next_tag(['tag_name' => 'a'])` would risk patching the wrong anchor. Fixed by adding a third `render_block_motto/container` filter (priority 10, after the background filter, before the existing Pro dynamic-link filter at priority 11) that reads the binding-resolved value from `$block_instance->attributes['linkContainerUrl']` (correctly populated by `WP_Block::process_block_bindings()` regardless of the selector issue — only the *write-back into HTML* was broken, not the resolution of the override's value) and splices it in itself via the same class-scoped `WP_HTML_Tag_Processor` lookup `motto_blocks_apply_container_link_override()` already used for the Pro case. Guarded by comparing the resolved value against the original (pre-binding) `$parsed_block['attrs']['linkContainerUrl']` so it only fires when an active override actually changed the value — normal (non-overridden) containers are untouched, since their raw saved markup already has the correct `href` baked in from `save()` and nothing needs patching. Registered before the Pro filter so dynamic mode still wins when both are present, matching §4.4's documented "dynamic always takes precedence" behavior. **Likely affects `motto/image` too** (SDD-025 also used a class selector, `.motto-image__media`, for `url`/`alt`/`title`) — its frontend override behavior was never explicitly verified in that spec's acceptance criteria (only "byte-identical markup for the *default*, non-overridden case" was checked); flagging for a follow-up, not fixed here (out of scope for this spec).
  2. **Confusing duplicate "Container Link" panel.** The `group="content"` split (required for the field to survive Gutenberg's "content only" editing mode inside a placed pattern instance — not optional UI polish, see §4.3) means the URL field and the toggle/dynamic fields necessarily live in two different Inspector tabs (Content vs. Settings) for *every* container, not just ones inside patterns — WP's tabbed Inspector shows both tabs unconditionally. The Settings-tab panel, now missing the URL field, read as a broken/empty duplicate of the Content-tab one. Not a bug in the override mechanism itself (same split shape as `motto/image`'s v0.5 "Image"/"Image" panels), but the identical panel title made it look like one. Renamed the default-group panel from "Container Link" to "Container Link Options" so the two panels read as related-but-distinct rather than an accidental duplicate; the content-group panel keeps the "Container Link" title since it's the one holding the actual link identity (its URL). Superseded by v0.4 — see below.
- v0.4: Follow-up discussion concluded the v0.3 rename was a workaround, not a fix — the real problem was rendering two permanent panels for a feature only a minority of containers use. Full redesign (`§4.1`, `§4.3`, `§4.5`; Rollout Phase D):
  - **Scope widened to match `core/button`'s actual precedent.** Re-checking core's real `wp-includes/blocks/button/block.json` showed it marks `linkTarget`/`rel` `role: "content"` alongside `url`, not just the URL — the earlier "toggles are out of scope" call in v0.1 was an unexamined assumption carried over from `motto/image` (which genuinely has no toggle-equivalent), not a technical limit. `linkContainerNewTab`/`linkContainerNoFollow` gained `role: "content"` (no `source`, reusing the `mediaId` precedent) rather than being converted to string mirrors of `target`/`rel` (core's literal approach), which would have been a breaking attribute-shape change for no real user-facing benefit.
  - **Single conditional panel, not a permanent split.** The "Container Link" panel (URL + both toggles, one `MottoLinkControl` instance) now renders in `group="content"` only when an override is actually active (`attributes.metadata.bindings`), and inline in the default group at its original position otherwise. A normal container (the overwhelming majority) sees the exact same single panel it always has — the split is now a consequence of actually using the feature, not a permanent tax on every container.
  - **Dynamic Link fully separated.** Since dynamic mode isn't overridable and doesn't belong in either state of the conditional panel, it moved into its own always-present, always-default-group "Dynamic Link" panel. `MottoLinkControl` traded its now-dead `hideUrl`/`hideToggles` props (from v0.2/v0.3's always-split design) for `dynamicOnly` (render only the dynamic section) and `dynamicLabel` (override the stub's heading text — container passes `"Enable"` since the panel title already says "Dynamic Link").
  - **Frontend splice extended.** `includes/container-render.php`'s v0.3 splice filter and `motto_blocks_apply_container_link_override()` were extended to resolve and write `target`/`rel` from `linkContainerNewTab`/`linkContainerNoFollow` overrides, not just `href` — WP's own `replace_html()` was never going to help here regardless of the class-selector issue, since these two attributes have no `source` for it to key off of at all.
  - **Naming convention softened.** `docs/conventions` doesn't own this file — `.claude/skills/motto-visual-system/references/panel-structure.md`'s "sub-panel titles are short nouns, avoid Settings/Options/Controls suffixes" rule was loosened to a suggestion (with an explicit exception example for this exact paired-panel case), after concluding the naming exercise here was a case the original rule didn't anticipate and enforcing it literally ("Link"/"Dynamic") would have made the pairing *less* legible, not more.
  - Chosen names: **"Container Link"** (content-group-when-active / default-group-otherwise panel) and **"Dynamic Link"** (always-default-group panel), deliberately not shortened to bare nouns — see §4.5.
  - Not yet empirically verified: whether "Enable overrides" actually sets `metadata.bindings.__default` as `hasLinkOverride` assumes (§7); whether new-tab/no-follow overrides actually reach the frontend `<a>`'s `target`/`rel`. `npm run lint`, `node scripts/validate-import-boundaries.mjs`, and `npm run build` all pass.
- v0.5: Live-verified — the URL override reaches the frontend correctly (both `hasLinkOverride` detection and the class-selector splice from v0.3/v0.4 work as designed), but the user reported the "Open in new tab" toggle override had no effect on the rendered `<a>`. Root cause: the priority-10 splice filter's early-return guard (`if ('' === $resolved_url) return $html;`) was keyed *only* on `linkContainerUrl`. `linkContainerUrl` has a `source`, so it's omitted from the parsed block comment on freshly-saved content — when an instance's override only customizes `linkContainerNewTab`/`linkContainerNoFollow` (the URL itself left at the pattern's value), `$resolved['linkContainerUrl']` never got populated by `process_block_bindings()` and fell back to the schema default `""`, tripping the early return and skipping the *entire* splice — including the `target`/`rel` write-back that had nothing to do with the URL. The link itself still "worked" (looked correct) purely because the untouched original markup already had the pattern's own href baked in from `save()`, masking the bug as a toggle-only failure rather than a broken link. Fixed by having `$resolved_url` fall back to `$original_url` when the resolved value is empty, instead of treating "no resolved URL" as "no override at all" — `$has_override`'s three-way comparison (url/new-tab/no-follow) now correctly drives the splice independent of which specific attribute an instance's override actually touched. `includes/container-render.php` updated; `npm run build` re-run to redeploy to the assembled plugin dirs. Still not independently re-verified in the browser after this fix — next test should confirm both the original URL-override case and the new-tab-only case.
