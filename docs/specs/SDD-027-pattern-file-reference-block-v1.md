# Feature Spec: SDD-027-pattern-file-reference-block-v1
Version: 0.8
Status: Active
Owner: Blocks (Pro)
Last Updated: 2026-08-06

## 1. Goal
Let editors insert a read-only reference to a block pattern authored as a `.php` file under the **active theme's own `patterns/` directory**, via a dedicated Pro block (`motto/pattern-ref`, displayed as **"Motto PHP Patterns"**), so patterns can be reused across posts/pages without depending on WordPress's native pattern inserter (which the user reports is hidden/unreliable in their editor) and without content drifting from the source file.

## 2. Scope
In scope:
- Identifying which patterns already auto-registered by WordPress core came from the active theme's (and, for a child theme, its parent's) `patterns/` directory, via `WP_Theme::get_block_patterns()` — no separate plugin-owned pattern directory or duplicate registration.
- A small REST route (`motto-blocks-pro/v1/theme-patterns`) exposing just those patterns (`name`, `title`, `content`) for the block's own picker, since Gutenberg's editor-bootstrap pattern data (`__experimentalBlockPatterns` / `core/block-patterns` store) proved unreliable across WP versions during implementation.
- New dynamic Pro block `motto/pattern-ref` ("Motto PHP Patterns") storing only a `patternSlug` string attribute.
- Editor placeholder/picker listing only theme-sourced patterns (title + preview thumbnail, in an isolated `BlockPreview` iframe).
- Read-only canvas rendering of the selected pattern (no inline editing, no "Convert to regular blocks"), rendered directly in the editor canvas document via `__experimentalUseBlockPreview` — no nested iframe, since the canvas is already inside the editor's own styled iframe.
- Frontend rendering via a PHP render callback, resolving the pattern by slug and running its content through `do_blocks()`.
- Graceful handling when a referenced slug no longer exists (renamed/deleted file, or the active theme changed).
- Styler CSS for `mottoStyler`-tagged blocks living inside a referenced pattern must reach `wp_head` on the *referencing* post, not just render correctly in the DOM.
- Using `motto/pattern-ref` as a Query Loop item template (v0.8): the block declares `"usesContext": ["postId"]` and, in the editor, prefers the loop-provided `context.postId` over the page being edited when present — so a "card" pattern with current-post-dependent content (dynamic background, `post-title`, etc.) resolves per loop item, not against the outer archive/listing page.
- Product packaging: this is a Pro-only, hard-gated block (`config/features.json`, `tier: "pro"`, `gate: "hard"`) — same tier as `marquee`/`conditional`/`panel-trigger`, not `motto-dynamics` (a separate product for query/data-driven content; this block references static-but-PHP-executable content, it doesn't bind to queries or dynamic data).

Out of scope:
- Editing pattern content from within `motto/pattern-ref` itself.
- Discovering patterns from any source other than the active theme's `patterns/` directory (other plugins, synced `wp_block` patterns). A plugin-owned pattern directory was the original v0.1 design; it was replaced in v0.2 — see §10.
- Hiding theme patterns from WordPress's native pattern inserter/Patterns tab. v0.1 forced `inserter: false` on plugin-owned patterns; that doesn't apply here — these are the theme's own patterns, and suppressing their native visibility site-wide would be an opinionated side effect this block shouldn't own.
- Pattern categories/tag UI beyond a flat list in the picker.
- Cache invalidation strategy beyond WordPress's own per-request behavior (core already re-scans the theme's `patterns/` directory on every `init`; this block just reads what core already registered).
- Live-reload of the block's canvas preview while a pattern file is being edited on disk (requires a full editor reload).
- Making the referenced pattern content itself dynamic (e.g. consuming `motto-dynamics` wildcards/query context). If that capability is added later, it would be the concrete justification to reconsider ownership; as shipped, this block has no dependency on `motto-dynamics`.
- Shortcode expansion in the picker's thumbnail previews (v0.6 only fixed the canvas instance preview). The picker still uses client-parsed `BlockPreview`, so a shortcode shows as literal `[bracket]` text there — accepted, since the picker is a selection aid, not the primary editing view.

## 3. Current Behavior
WordPress core already auto-registers every `.php` file under the active theme's `patterns/` directory on `init` (`_register_theme_block_patterns()`, `wp-includes/block-patterns.php`), using `WP_Theme::get_block_patterns()` for header parsing and `WP_Block_Patterns_Registry`'s `filePath` hand-off for output-buffered content loading. The native `core/pattern` block + pattern inserter modal already provide roughly the read-only-reference behavior being asked for (frontend runs the registered pattern's content through `do_blocks()`; editor shows a preview that stays non-editable unless the user explicitly detaches it) — but the picker UI mixes in every registered pattern from every source (theme, core, other plugins), and the user reports it's hidden/unreliable in their current editor setup.

## 4. Target Behavior
1. `pro/includes/pattern-ref-render.php` does **not** register any patterns itself. `motto_pro_get_theme_pattern_slugs()` calls `wp_get_theme()->get_block_patterns()` (and the parent theme's, if any) to get the slugs WordPress core considers theme-sourced, independent of whether core's own `init` hook has run yet.
2. `motto_pro_get_theme_patterns()` cross-references those slugs against `WP_Block_Patterns_Registry::get_instance()`, returning `{ name, title, content }` for each one that's actually registered.
3. `GET /wp-json/motto-blocks-pro/v1/theme-patterns` (REST, `edit_posts`-gated) exposes that list to the editor.
4. `motto/pattern-ref` block.json defines a single attribute, `patternSlug` (string, default `""`); `title` is `"Motto PHP Patterns"`.
5. Editor, empty state (`patternSlug === ""`): placeholder fetches the REST route on mount and shows a list of theme-sourced patterns (title + `<BlockPreview>` thumbnail per candidate, each in its own isolated iframe). Selecting one sets `patternSlug`.
6. Editor, filled state (v0.6): canvas fetches server-rendered HTML for the current `patternSlug` from `/wp/v2/block-renderer/motto/pattern-ref?context=edit` — i.e. the block calls its *own* render callback over REST — and injects it via `dangerouslySetInnerHTML` into a `pointer-events: none` wrapper (CSS-enforced read-only, since raw injected HTML carries no Gutenberg interactivity guard the way `__experimentalUseBlockPreview`, used through v0.5, did). A button in the Inspector ("Change pattern") clears `patternSlug` back to the picker state. This replaced client-side block-tree rendering specifically so editor and frontend run through the *same* PHP code path — see item 12.
7. Frontend + editor render callback (`motto_pro_render_pattern_ref_block()`): looks up `WP_Block_Patterns_Registry::get_instance()->get_registered( $attributes['patternSlug'] )`; if found, outputs `do_shortcode( do_blocks( $pattern['content'] ) )` (v0.6 added the explicit `do_shortcode()` — see item 12); if not found, outputs nothing.
8. Editor, missing-slug state (slug set but not present in the REST response): show a `Warning` instead of an empty or broken preview; do not fatal.
9. Frontend Styler CSS collection (`includes/styler-frontend-render.php` — **Free**, not Pro): the per-post cached-CSS snapshot builder (`motto_styler_collect_parsed_blocks_into_snapshot()`) already has explicit resolvers for other "reference" block types — `core/block` (reusable), `core/template-part`, `core/navigation`'s overlay — that pull in the referenced content's parsed blocks so their `mottoStyler` CSS gets included. `motto/pattern-ref` needed the same treatment: `motto_styler_get_pattern_ref_slug()` + `motto_styler_get_pattern_ref_parsed_blocks()` resolve the referenced pattern via `WP_Block_Patterns_Registry` (mirroring the render callback's own resolution) and recurse into it, deduped via `$ctx['visitedPatternRefs']`. Without this, `mottoStyler` CSS on blocks inside a referenced pattern would render correctly in the DOM (class gets applied) but never appear in `wp_head` for cacheable post types, since that path is a static pre-scan of `post_content`, not "whatever actually rendered." This resolver stays in Free regardless of the block's Pro ownership — see §7.1.
10. Product packaging (`config/features.json`): registered as `slug: "pattern-ref"`, `name: "Motto PHP Patterns"`, `category: "block"`, `tier: "pro"`, `gate: "hard"`. Free's Blocks admin tab reads this catalog to show a "Get Pro" card — Free does not register the real block or ship its assets, same as `panel-trigger`/`marquee`/`conditional`.
11. Editor canvas Styler CSS (v0.5 — `docs/conventions/styler-css-loading.md` Path 4): `motto_pro_build_pattern_styler_css()` (`pro/includes/pattern-ref-render.php`) reuses Path 3's own builder functions (`motto_blocks_collect_template_preview_styler_css()`, `motto_styler_build_frontend_styles_css()`, `motto_styler_build_css_class_rules()`) scoped to one pattern's content, and returns the result as a `stylerCss` field on every entry in the `/theme-patterns` REST response. The block's filled-state canvas renders `<style>{selectedPattern.stylerCss}</style>` next to the server-rendered preview. Confirmed empirically that this was necessary: Path 3's `block_editor_settings_all` CSS injection targets real `BlockPreview` iframes (which the picker's thumbnails still use, so they already got this for free) — it does not reach a block's own non-iframe React output, so the v0.2 canvas-instance iframe removal had silently dropped Styler CSS from that specific view until this fix. Unaffected by the v0.6 switch to server-rendered HTML — `stylerCss` is a separate REST field from the rendered markup, not something `motto_pro_render_pattern_ref_block()` prints itself.
12. Shortcode support in the editor canvas (v0.6): a shortcode inside a pattern (e.g. `[my_shortcode]` as literal text in a paragraph) rendered correctly on the frontend already, but only "by accident" — the surrounding page's `the_content` filter chain runs `do_shortcode` (priority 11) *after* `do_blocks` (priority 9) on the whole assembled string, which happened to also expand whatever unexpanded shortcode text our render callback's output carried. The editor's `__experimentalUseBlockPreview`-based canvas (v0.2–v0.5) could never show this: it's a pure client-side React re-render of the parsed block tree, and shortcodes are PHP-only — no client rendering path can execute them. Fixed in two parts: (a) `motto_pro_render_pattern_ref_block()` now calls `do_shortcode()` explicitly rather than relying on the surrounding page's pipeline, making expansion deterministic regardless of context (including isolated `block-renderer` calls, which have no `the_content` wrapper at all); (b) the canvas instance preview switched from client-side block-tree rendering to fetching this same render callback's actual output over REST (item 6) — the only way for editor and frontend to guarantee identical output, since a shortcode's result is arbitrary PHP output that a client-side re-render can never reproduce.

13. Current-post context for the server-rendered preview (v0.7): content inside a pattern that resolves against "the current post" server-side — e.g. a Pro `motto/container` background image in `backgroundDynamic` featured-image mode — needs `WP_Block`'s `postId` context, which WP core's `render_block()` seeds from the global `$post` variable (`if ( $post instanceof WP_Post ) { $context['postId'] = $post->ID; ... }`, `wp-includes/blocks.php`). On the frontend, global `$post` is already correct for the whole request. The isolated `block-renderer` REST call has none unless told — `index.jsx` now passes `post_id: currentPostId` (from `select('core/editor').getCurrentPostId()`) in the request body; `WP_REST_Block_Renderer_Controller::get_item()` sets `global $post` from it before calling `render_block()`, and since that's the same PHP global for the rest of the request, it also reaches the nested `do_blocks()` call inside `motto_pro_render_pattern_ref_block()` — not just our own block's top-level context.

14. Query Loop item context (v0.8): `block.json` declares `"usesContext": ["postId"]`. In `edit()`, `context.postId` (provided automatically by Gutenberg when the block is nested inside a Query Loop's item template, e.g. `core/post-template`) takes priority over `select('core/editor').getCurrentPostId()` — the latter is used only as a fallback for standalone usage. The resolved value feeds the same `post_id` REST parameter from item 13. Verified against a real Query Loop (`core/query` + `core/post-template` + `motto/pattern-ref`) with two posts carrying different featured images: per-instance debug output confirmed `context.postId` matched each loop iteration's actual post ID, and each instance's resolved background image matched that specific post's featured image — not the outer page's. The frontend needed no corresponding change: Query Loop rendering already sets the ambient global `$post` per iteration via `the_post()`, which `render_block()` (item 13) reads directly regardless of block context.

## 5. Data Contract
- Inputs:
  - `{active theme}/patterns/*.php` (and parent theme, for child themes) — entirely WordPress core's own file-header + content contract (`WP_Theme::get_block_patterns()`); this addon does not define or extend that contract.
- Persistence:
  - `motto/pattern-ref` block attribute: `patternSlug` (string). No postmeta/options usage — resolution happens by slug at render/editor-load time against the live pattern registry, not by copying content into the block.
- Outputs:
  - REST: `GET /motto-blocks-pro/v1/theme-patterns` → `[{ name, title, content, stylerCss }]`.
  - Editor: picker thumbnails via isolated `BlockPreview` (gets Styler CSS from Path 3 automatically, being a real iframe; client-parsed, so shortcodes and post-context-dependent content don't resolve there — accepted limitation, see §2 in-scope note); selected-instance canvas (v0.6, refined v0.7) via server-rendered HTML from `/wp/v2/block-renderer/motto/pattern-ref` sent with `post_id: <currently-edited post ID>` (same render callback the frontend uses, with the same current-post context — `dangerouslySetInnerHTML` into a `pointer-events: none` wrapper) + an inline `<style>{stylerCss}</style>` (Path 4, since there's no `BlockPreview` iframe for Path 3 to reach).
  - Frontend: raw HTML from `do_shortcode( do_blocks( ... ) )` on the registered pattern's content — output-equivalent to inserting the pattern's blocks directly or using core's `core/pattern` block, plus deterministic shortcode expansion (v0.6).
  - Frontend Styler CSS: the referencing post's `wp_head` output includes `.motto-styler-<instanceId>{...}` rules for any `mottoStyler`-tagged block found inside the referenced pattern's content, same as it already does for blocks inside a reusable block or template part.

- [x] Frontend output of a page containing `motto/pattern-ref` matches inserting the pattern's blocks directly — verified via a real published post rendering the pattern's heading/paragraph through `do_blocks()`.
- [ ] Renaming or deleting a referenced pattern file does not fatal the editor or frontend; both show a clear empty/not-found state instead. (Implemented; not re-verified after the v0.2 source change or the v0.4 Free→Pro move.)
- [x] Patterns registered from a source other than the active theme's `patterns/` directory do not appear in this block's picker (the REST route only ever returns `WP_Theme::get_block_patterns()`-sourced slugs).

## 7. Risks and Mitigations
- Risk: `WP_Theme::get_block_patterns()`'s own dev-mode pattern cache (`wp_is_development_mode('theme')`) could serve a stale slug list after a pattern file is added/removed outside of theme dev mode.
  - Mitigation: matches core's own caching behavior exactly (this block adds no caching of its own); acceptable for v1, revisit only if it causes real confusion.
- Risk: Pattern content references blocks unavailable at render time (e.g. another Pro-only block while Pro is deactivated), producing broken markup.
  - Mitigation: `do_blocks()` already degrades unknown block comments gracefully in core; add a manual check with a Pro-only block reference while Pro is off.
- Risk (superseded in v0.6): Gutenberg's `__experimentalUseBlockPreview` (an explicitly experimental/internal API) powered the canvas instance preview from v0.2–v0.5. It's no longer used anywhere in this block (replaced by the server-rendered `block-renderer` approach), so this risk no longer applies — kept here only as history, since the same "experimental API" risk class is exactly what motivated moving pattern *discovery* off `__experimentalBlockPatterns` earlier too.
- Risk: The v0.6 server-rendered canvas preview uses `dangerouslySetInnerHTML` with no Gutenberg-provided interactivity guard (unlike `__experimentalUseBlockPreview`, which disabled interaction itself) — read-only-ness is enforced only by CSS (`pointer-events: none` on the wrapper), same technique already used for the picker's thumbnail previews and for `classic-menu`'s own server-rendered preview elsewhere in this repo.
  - Mitigation: verified 0 `[contenteditable]` elements and no click-through in manual testing; if a future pattern's content relies on JS-driven interactivity that `pointer-events: none` would break in a way that matters for the preview's legibility, revisit scoping the CSS more narrowly (e.g. only block real form controls) rather than removing it outright.
- Risk: `do_shortcode()` executes arbitrary registered shortcode callbacks, which can run arbitrary PHP (including side effects, not just output).
  - Mitigation: accepted — pattern files are theme code authored by a trusted developer/agency, not end-user input; this is the same trust boundary theme `patterns/*.php` files already operate under (they're literally executable PHP via the `filePath`/`include` mechanism WP core itself uses), and matches how `the_content`'s own `do_shortcode` already behaves for any post referencing the same shortcode today.
- Risk: The Styler frontend CSS cache (`_motto_styler_front_css` postmeta) is rebuilt on the *referencing* post's `save_post`, not when the pattern file itself changes on disk. Editing a theme pattern file's Styler-tagged blocks after a referencing post was last saved leaves that post's cached CSS stale until it's re-saved.
  - Mitigation: not addressed in v1 — same class of limitation as editing a reusable block/template part already has in this system (no generic "who references me" invalidation for anything). Revisit only if this causes real confusion in practice; a theme pattern file's Styler content is expected to be far more stable than page content.
- Risk: `motto_pro_build_pattern_styler_css()` recomputes CSS for every pattern on every `/theme-patterns` request (no caching), same brute-force characteristic Path 3 already has for its whole-site sweep.
  - Mitigation: acceptable at expected pattern-catalog sizes; the request only fires while a `motto/pattern-ref` block is actually being edited, not on every editor load site-wide.
- Risk (v0.7): content resolving against "the current post" (e.g. dynamic backgrounds, and potentially other Pro dynamic-content features not yet audited) depends on `render_block()`'s built-in `postId`-from-global-`$post` context seeding. This is a general WP core mechanism, not something this block controls directly — if a future WP core version changes how/whether `render_block()` seeds this context, or if some other Pro dynamic-content resolver reads post context a different way (e.g. directly from `$wp_query`/`get_queried_object()` instead of `$block->context['postId']`), the same class of bug could resurface for that specific feature even with `post_id` correctly passed.
  - Mitigation: verified specifically for `backgroundDynamic` (featured-image mode) via a real draft post with `featured_media` set; other Pro dynamic-content resolvers using the same `motto_pro_resolve_context_post_id()`/`motto_pro_resolve_current_term_id()` pattern (`pro/includes/dynamic-image-resolver.php`) should behave the same way, but weren't individually re-tested.

## 7.1 Consumers of the New Pattern-Reference Resolver
`motto_styler_get_pattern_ref_slug()` / `motto_styler_get_pattern_ref_parsed_blocks()` live in `includes/styler-frontend-render.php` (**Free's** core Styler engine, not Pro) and are dispatched in `motto_styler_collect_parsed_blocks_into_snapshot()` for any block named `motto/pattern-ref`, regardless of which addon actually registers that block type. This keeps the Styler CSS engine's existing "reference block" resolution pattern (`core/block`, `core/template-part`, `core/navigation` overlay) consistent without creating a Free→Pro dependency — the resolver only pattern-matches a block name string and calls `WP_Block_Patterns_Registry`, a WP core API. It stayed in Free even after the block itself moved to Pro in v0.4, same as it already resolves native `core/*` reference blocks it doesn't own.

## 10. Change Log
- v0.1: Initial draft — plugin-owned `pattern/*.php` directory, custom category marker, `inserter: false`, `BlockPreview` (iframe) for both picker and canvas instance.
- v0.2: Implemented and verified end-to-end, then redesigned per follow-up direction:
  - Pattern source changed from a plugin-owned `pattern/` directory to the **active theme's own `patterns/` directory** — this plugin no longer registers any patterns itself, it only identifies which of core's already-registered patterns came from the theme (`WP_Theme::get_block_patterns()`), dropping the custom category marker and the `inserter: false` override entirely.
  - Picker data source changed from Gutenberg's `core/block-patterns` store / `__experimentalBlockPatterns` (found unreliable — absent/empty in a real WP 7.0.1 install during verification) to a dedicated REST route.
  - Canvas instance preview (filled state) changed from iframe-based `BlockPreview` to non-iframe `__experimentalUseBlockPreview`, since the canvas already runs inside the editor's own styled iframe. Picker thumbnails keep `BlockPreview` (iframe) unchanged.
- v0.3: Fixed a real gap found while reviewing this spec against `docs/conventions/styler-css-loading.md`: the frontend Styler CSS cache builder (Path 1's cached fast path) had no resolver for `motto/pattern-ref`, so `mottoStyler` CSS on blocks inside a referenced pattern rendered correctly in the DOM but never reached `wp_head` for cacheable post types. Added `motto_styler_get_pattern_ref_slug()` / `motto_styler_get_pattern_ref_parsed_blocks()` + a dispatch case in `motto_styler_collect_parsed_blocks_into_snapshot()` (`includes/styler-frontend-render.php`), mirroring the existing `core/block`/`core/template-part` resolvers. Verified via a real published post + a temporary theme pattern containing a styled `core/paragraph`.
- v0.4: Product-packaging decision (discussed against `motto-dynamics` as an alternative owner; rejected — Dynamics is defined by queries/data-binding, this block references static-but-PHP-executable content with no data binding, so Pro is the correct tier/owner): renamed display title to **"Motto PHP Patterns"** (block name stays `motto/pattern-ref`); moved the block from Free (`motto-blocks`) to Pro (`motto-blocks-pro`) as a hard-gated block, mirroring the existing `marquee`/`conditional`/`panel-trigger` pattern — `src/blocks/pattern-ref/` → `src/pro/blocks/pattern-ref/`, `includes/pattern-registry.php` → `pro/includes/pattern-ref-render.php` (functions renamed `motto_blocks_*` → `motto_pro_*`), REST namespace `motto-blocks/v1` → `motto-blocks-pro/v1`, registration moved from `motto-blocks.php` to `pro/motto-blocks-pro.php`, added a `config/features.json` catalog entry (`tier: "pro"`, `gate: "hard"`). The Free-owned Styler CSS resolver added in v0.3 was deliberately left in Free — see §7.1.
- v0.5: Closed a follow-up gap found by direct empirical check (inspecting the canvas iframe's `<style>` tags + computed `background-color`): the non-iframe canvas instance preview (introduced in v0.2) does not receive Styler CSS the way the picker's iframe-based `BlockPreview` thumbnails do. Root cause: `docs/conventions/styler-css-loading.md`'s Path 3 (`block_editor_settings_all`) only reaches real `BlockPreview` iframes, and this preview deliberately has none. Rather than force-fitting the fix into Path 3, documented a new **Path 4** in that doc (block-level, no-iframe preview CSS delivered via REST + inline `<style>`, reusing Path 3's builder functions but scoped to one pattern) and implemented it: `motto_pro_build_pattern_styler_css()` adds a `stylerCss` field to each `/theme-patterns` REST entry; the block renders it as `<style>{stylerCss}</style>` beside the non-iframe preview.
- v0.6: Fixed shortcode support in the editor canvas, found by the user testing a shortcode inside a pattern and seeing it render on the frontend but not in the editor. Root cause was two-fold: (1) `motto_pro_render_pattern_ref_block()` never called `do_shortcode()` itself — the frontend "worked" only because the surrounding page's `the_content` pipeline happens to run `do_shortcode` after `do_blocks` on the whole assembled string; (2) the canvas instance preview (`__experimentalUseBlockPreview`, client-side block-tree rendering) can structurally never run PHP, so no amount of client-side work could have shown shortcode output there. Fixed by making `do_shortcode()` explicit in the render callback, and by replacing the canvas instance preview with a fetch of that same render callback's actual output via `/wp/v2/block-renderer/motto/pattern-ref?context=edit` (the same technique `classic-menu` already uses elsewhere in this repo), rendered via `dangerouslySetInnerHTML` in a `pointer-events: none` wrapper to keep it read-only without Gutenberg's block-tree interactivity guard. Editor and frontend now run through the literal same PHP code path — not just visually equivalent output. Picker thumbnails were deliberately left unchanged (still client-parsed `BlockPreview`, so shortcodes don't expand there) since they're a selection aid, not the primary editing view.
- v0.7: Fixed a second post-v0.6 gap, found by the user testing a Pro dynamic (featured-image) `motto/container` background — it rendered on the frontend but not in the (new, v0.6) server-rendered canvas, and the user noted it *had* worked under the old v0.2–v0.5 client-side preview. Root cause: WP core's `render_block()` seeds a block's `postId` context from the global `$post` variable (`wp-includes/blocks.php`) — correct on the frontend for the whole request, but our isolated `block-renderer` REST call had no post context at all, so `motto_pro_resolve_context_post_id()` (`pro/includes/dynamic-image-resolver.php`) had nothing to resolve against. Fixed by passing `post_id: currentPostId` (from `select('core/editor').getCurrentPostId()`) in the `block-renderer` request; `WP_REST_Block_Renderer_Controller` sets `global $post` from it before rendering, and because that's the same PHP global for the rest of the request, it also reaches the nested `do_blocks()` call inside our own render callback — no PHP changes needed, this was purely a missing REST parameter. Verified against a real draft post with `featured_media` set. Surfaced a real, deliberately out-of-scope gap for later — see §2's Query Loop item-template note.
