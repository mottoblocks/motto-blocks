# Feature Spec: SDD-024
Version: 0.3
Status: Active
Owner: Blocks
Last Updated: 2026-08-05

## 1. Goal
Bring `motto/accordion-item`'s trigger content model in line with `motto/tab-button`'s post-SDD-022 shape: replace the `label`/`iconOptions`/`iconPosition`/`customIcon` attributes (+ their custom Inspector UI, + the shared `TabTriggerContent`/`TabTriggerEditor` components) with real `InnerBlocks` (a text block + an optional `motto/svg` icon block). Because `accordion-item`'s existing `InnerBlocks` slot is already the free-form **panel** content, this requires splitting `accordion-item` into an outer wrapper plus two new fixed children — `motto/accordion-trigger` (text + optional icon) and `motto/accordion-panel` (the existing free-form panel content, unchanged) — mirroring `motto/tabs`'s `tab-container`/`tab-panels` split, while explicitly avoiding the `templateLock: "all"` + nested-`template` regression found and fixed in SDD-022 (§4.5 there).

## 2. Scope
In scope:
- New block `motto/accordion-trigger`: `InnerBlocks` container, `allowedBlocks: ["core/paragraph", "motto/svg"]`, default template `[["core/paragraph", { content: "Accordion item" }]]` (real text, matching SDD-022's "new tab shows real text, not an empty placeholder" fix — not a placeholder here either), `templateLock: false`. Renders the actual `<button class="motto-accordion-item__trigger">` (must stay a **direct child** of `.motto-accordion-item` in the DOM — `accordion-frontend.js` queries `:scope > .motto-accordion-item__trigger`) plus the existing fixed, non-optional chevron (`lucide-react` `ChevronDown`, unaffected by this change).
- New block `motto/accordion-panel`: thin wrapper block carrying today's `accordion-item`'s panel `InnerBlocks` verbatim (unrestricted `allowedBlocks`, `templateLock: false`, default template `[["core/paragraph", { placeholder: "Accordion content…" }]]`). Renders `<div class="motto-accordion-item__panel"><div class="motto-accordion-item__panel-inner">...</div></div>` — again must stay a direct child of `.motto-accordion-item` (same `:scope >` constraint).
- `motto/accordion-item` becomes the outer wrapper: keeps `itemId`/`isOpen` attributes and all existing open-state computation (`isEditorOpen`, `AccordionEditorContext` ephemeral state, `closeOtherItems` mutual exclusion) and its own root `<div class="motto-accordion-item">`, but no longer renders the trigger `<button>` or panel `<div>` directly — instead has a **deliberately shallow** `TEMPLATE = [[ACCORDION_TRIGGER_BLOCK], [ACCORDION_PANEL_BLOCK]]` (no nested arrays — see §4.5/Risks) with `templateLock: "all"`, and seeds the two children itself via a `useEffect` the first time both are empty (mirrors `motto/tabs`' `DEFAULT_TAB_SEEDS` pattern from SDD-022, not WP's native per-mount template re-application).
- New block context: `motto/accordion-item` provides `itemId`/`isOpen` (`providesContext: { "motto/accordion-item-itemId": "itemId", "motto/accordion-item-isOpen": "isOpen" }`) down to `accordion-trigger`/`accordion-panel`, mirroring `motto/tabs`' `activeTabId` context. `AccordionEditorContext` (the existing React context for ephemeral editor-preview open state) is unaffected — it's already provided at the top `motto/accordion` level and reaches descendants regardless of the new nesting.
- Toggle-click logic (today's `handleToggle` in `accordion-item`) moves to `motto/accordion-trigger`'s own `onClick`, reading `itemId`/`closeOtherItems` via context + `AccordionEditorContext`, and updating the parent `accordion-item`'s `isOpen` attribute via `updateBlockAttributes` (found via `getBlockParents`, mirroring `useTabButtonContext`). No forced `selectBlock` call on click (per SDD-022's lesson — with real child blocks inside the trigger, clicking the paragraph/icon should select that child, not get hijacked back to the trigger).
- Remove the now-obsolete Inspector UI on `motto/accordion-item` for label/icon (`ToggleControl` "Show custom icon", `IconPositionToggle`, `ButtonIconSelector`) — the "Open by default" toggle stays (it's about `isOpen`, unrelated to trigger content).
- Update `block.json`/`README.md` for `accordion`, `accordion-item`, and the two new blocks.
- Audit accordion for the SDD-022-class bugs even though the architecture looks structurally safer (see §3, §7) — verified empirically via a new `tests/e2e/accordion.spec.mjs`, not assumed from code reading alone.
- `npm run build` to refresh tracked build artifacts.

Out of scope:
- The `closeOtherItems` / multi-item-open behavior model itself — unchanged, and deliberately different from tabs (see §4.6, Functional Differences).
- ARIA/keyboard-nav gaps, if any exist beyond what's already implemented (accordion already has more ARIA wiring than tabs — `aria-expanded`, `aria-controls`, `aria-labelledby`, `role="region"` — this spec preserves it, doesn't audit it further).
- Any Pro gating.
- Height-measurement/animation runtime (`accordion-frontend.js`'s `ResizeObserver` + CSS var mechanism) — untouched, still keyed off the same class names.
- ~~A `deprecated` entry~~ — **reversed after shipping, see §4.8**: the "accordion confirmed unused in production" premise this spec shipped under was wrong. Real published content on a live client site (`housing-hub`) used `motto/accordion-item` with `label`/`customIcon`/`iconOptions` set, and broke (showed as invalid blocks) the moment this spec's `block.json` changes went live. A `deprecated`/`migrate()` entry was added as a follow-up, verified against the real affected content.

## 3. Current Behavior (pre-SDD-024)
- `motto/accordion-item` is a single, self-contained block: `label`/`customIcon`/`iconOptions`/`iconPosition` attributes render a trigger `<button>` via shared `TabTriggerContent`/`TabTriggerEditor` (same components `motto/tab-button` used **before** SDD-022), plus a fixed `ChevronDown` icon, plus its own free-form panel `InnerBlocks` (default template `[["core/paragraph", { placeholder: "Accordion content…" }]]`, no `allowedBlocks` restriction).
- `motto/accordion`'s own `TEMPLATE` (`[[ACCORDION_ITEM_BLOCK, { label: "Item 1" }], [ACCORDION_ITEM_BLOCK, { label: "Item 2" }]]`) uses `templateLock: false` (not `"all"`) — structurally different from `motto/tabs`. Per `useInnerBlockTemplateSync`'s logic (read directly from the installed WP core bundle during SDD-022's investigation), `shouldApplyTemplate` is only forced `true` for `templateLock === "all"`/`"contentOnly"`; for `false`, it's only `true` when `currentInnerBlocks.length === 0`. This means `motto/accordion` **does not** re-apply its template destructively on remount the way `motto/tabs` did pre-SDD-022-fix — it's already immune to that specific regression by construction.
- The item-id-dedup `useEffect` in `motto/accordion` only ever calls `updateBlockAttributes` (never `replaceInnerBlocks`) — there is no cross-list "orphan repair" mechanism like `motto/tabs` has, because there's nothing to reconcile: trigger and panel have always been part of the **same** block (`accordion-item`), never two independent lists needing id-matched reconciliation. This means the specific empty-id/duplicate-id race conditions found and fixed in `motto/tabs` (SDD-022 §4.4) have no direct equivalent here today.
- `TabTriggerContent`/`TabTriggerEditor`/`normalizeTabIconPosition` (`src/components/ui/tabs/tab-trigger-content.jsx`) are, after SDD-022, used **only** by `motto/accordion-item` — `motto/tab-button` no longer imports them. This spec's trigger-content change would make this shared file fully unused (not deleted here — flagged as a candidate for a future, separate cleanup pass, out of scope for this spec).

## 4. Target Behavior

### 4.1 New block: `motto/accordion-trigger`
- `block.json`: `parent: ["motto/accordion-item"]`, `supports: { inserter: false, reusable: false }`, `usesContext: ["motto/accordion-item-itemId", "motto/accordion-item-isOpen", "motto/accordion-closeOtherItems"]`, no `mottoDefaults` (mirrors `motto/tab-button` — default styling for triggers stays on `motto/accordion`'s `blockSelectors`, already the case today).
- `edit()`: `useInnerBlocksProps` on the `<button>` root itself (mirrors `motto/tab-button` exactly): `allowedBlocks: ["core/paragraph", "motto/svg"]`, `template: [["core/paragraph", { content: "Accordion item" }]]`, `templateLock: false`. The fixed chevron (`ChevronDown`, `size={18}`) renders as a sibling after the `InnerBlocks` content, inside the same `<button>`, exactly where it renders today.
- `onClick` (replacing today's `accordion-item`-level `handleToggle`, relocated verbatim): reads `itemId`/`isOpen`/`closeOtherItems` via context + `AccordionEditorContext` and calls `setEditorActiveItemId`/`setEditorOpenItemIds` exactly per today's 3-branch logic (§Current Behavior's "Trigger click semantics"). **Simpler than planned once implemented**: no `getBlockParents`/parent-clientId lookup needed at all (unlike `useTabButtonContext`) — none of the 3 click branches persist `isOpen` (that only ever happens via the parent's own Inspector toggle), so there's no `updateBlockAttributes` call on click. No `selectBlock()` call — per SDD-022, clicking the button's text/icon children should select those children normally, not force-reselect the trigger.
- `save()`: `<button class="motto-accordion-item__trigger" ...><InnerBlocks.Content />{chevron}</button>` — must remain a **direct child** of `accordion-item`'s root div (no extra wrapper), since `accordion-frontend.js` queries `:scope > .motto-accordion-item__trigger`.
- **Revised during implementation** (see §4.7): also declares its own `itemId`/`isOpen` **attributes**, not just `usesContext` — `save()` has no access to block context, so the id/`aria-*` output at save/frontend-render time needs real persisted values on this block itself, kept in sync one-way by the parent's own effect. `edit()` still reads the *live* context values (no sync lag), only falling back to the duplicated attributes in `save()`.

### 4.2 New block: `motto/accordion-panel`
- `block.json`: `parent: ["motto/accordion-item"]`, `supports: { inserter: false, reusable: false }`, `usesContext: ["motto/accordion-item-itemId", "motto/accordion-item-isOpen"]`, **plus its own `itemId`/`isOpen` attributes** (same §4.7 reason as the trigger).
- `edit()`/`save()`: carries over today's `accordion-item` panel rendering verbatim — `<div class="motto-accordion-item__panel" role="region" aria-labelledby={triggerId} aria-hidden={...}><div class="motto-accordion-item__panel-inner"><InnerBlocks/></div></div>`, default template `[["core/paragraph", { placeholder: "Accordion content…" }]]`, `templateLock: false`, no `allowedBlocks` restriction (unchanged permissiveness). `aria-hidden` is derived from the live `motto/accordion-item-isOpen` context value in `edit()`, from the duplicated `isOpen` attribute in `save()`.
- Must remain a direct child of `accordion-item`'s root div — same `:scope >` constraint as the trigger.

### 4.3 `motto/accordion-item` becomes the outer wrapper
- **Deliberately shallow `TEMPLATE`** (the SDD-022 §4.5 lesson, applied proactively rather than rediscovered the hard way): `[[ACCORDION_TRIGGER_BLOCK], [ACCORDION_PANEL_BLOCK]]` — **no nested arrays**. `accordion-item` itself now needs `templateLock: "all"` (to lock the 2-child trigger+panel structure), and per SDD-022, `templateLock: "all"` makes WordPress re-apply `TEMPLATE` via `synchronizeBlocksWithTemplate()` on **every mount**, capping any nested content at the template's literal length. Giving either child entry a 3rd (`innerBlocksTemplate`) array element would silently truncate a user's panel content (e.g. more than 1 paragraph) or trigger content the next time the post is reopened — exactly the bug fixed in SDD-022. Keeping both entries childless makes that recursion a no-op at every depth, permanently.
- **JS-based default seeding**, not native template content: a `useEffect` runs once, the first time both children are absent **and this item's own `itemId` is already resolved** (non-empty — gated so freshly-created children are never seeded with an empty id, which would need its own repair pass), seeding `accordion-trigger` with `[core/paragraph{ content: "Accordion item" }]` and `accordion-panel` with `[core/paragraph{ placeholder: "Accordion content…" }]` via `replaceInnerBlocks(clientId, [...], false)` — note this is a *single* `replaceInnerBlocks` call on `accordion-item`'s own clientId (unlike `motto/tabs`, which needs two separate calls against `tab-container`/`tab-panels`' clientIds, since here both children are already direct children of the same block). Fires exactly once; never re-touches real content on remount.
- **The same effect also pushes `itemId`/`isOpen` down** to the trigger/panel's own duplicated attributes (§4.7) whenever this block's values change and both children already exist — a plain one-way sync via `updateBlockAttributes`, never a `replaceInnerBlocks`/deletion, so it carries none of `motto/tabs`' race-condition risk (§4.6 explains why: trigger+panel can never independently drift into an "only one exists" state here).
- Keeps `itemId`, `isOpen` attributes and all existing open-state logic (`isEditorOpen` derivation — via the new shared `computeIsEditorOpen()` helper, `AccordionEditorContext` reads, `closeOtherItems`-driven mutual exclusion) — **unchanged**, just no longer renders the trigger/panel DOM directly; instead provides `itemId`/`isOpen` as new block context for the two children's live `edit()`-time reads.
- Root render becomes `<div className="motto-accordion-item ..." data-item-id={itemId}><InnerBlocks/></div>` with `allowedBlocks: [ACCORDION_TRIGGER_BLOCK, ACCORDION_PANEL_BLOCK]`, `templateLock: "all"`, `renderAppender: false` — same shape as `motto/tabs`'s own root. Still carries its own `.is-open` class (computed the same way as before SDD-024) — this remains the single source of truth `accordion.scss`'s chevron/panel-height CSS and `accordion-frontend.js`'s own state detection key off, unaffected by the split.

### 4.4 `motto/accordion` (parent) — minimal changes
- `TEMPLATE` stays `[[ACCORDION_ITEM_BLOCK], [ACCORDION_ITEM_BLOCK]]` — drops the `{ label: "Item 1" }`/`{ label: "Item 2" }` attribute seed (that attribute no longer exists on `accordion-item`). Distinct default text per item ("Item 1" vs "Item 2") is **not** preserved by this template — see §4.6/Functional Differences for why, and the accepted alternative (both default to generic "Accordion item", matching how a manually-appended `tab-button` defaults to generic "Tab" rather than a numbered label).
- `templateLock` stays `false` — already safe (§3), no change needed here to avoid the SDD-022 remount bug.
- The existing item-id-dedup `useEffect` is unchanged (still only calls `updateBlockAttributes`, never deletes).

### 4.5 Why this needs to be shallow (recap of the SDD-022 finding, applied here proactively)
See SDD-022 §4.5 for the full mechanism (`useInnerBlockTemplateSync`'s `shouldApplyTemplate` being unconditionally `true` for `templateLock: "all"`, and `synchronizeBlocksWithTemplate`'s `template.map(...)` silently capping content at the template's literal length, recursively). The only **new** `templateLock: "all"` surface this spec introduces is `motto/accordion-item`'s own 2-child trigger/panel lock — designed shallow from the start per §4.3, rather than discovered as a regression after shipping (as happened in `motto/tabs`).

### 4.6 Functional Differences from `motto/tabs` (SDD-022) — explicit, as requested
- **No cross-list id-matching / orphan-repair mechanism needed.** `motto/tabs` needed 4 `useEffect`s because buttons and panels live in two independent sibling lists (`tab-container`/`tab-panels`) that must stay in sync by `tabId`. Here, trigger and panel are always direct children of the **same** `accordion-item` — 1:1 by construction, nothing to reconcile across lists. This eliminates the entire class of empty-id/duplicate-id races SDD-022 had to guard against (§4.4 there) — there is no equivalent guard needed in `accordion-item`'s seed effect, since it isn't matching two lists, just seeding its own two fixed children once.
- **Multiple items can be open simultaneously** (unless `closeOtherItems` is on) — vs. tabs' single-active-tab model. This governs `isOpen`/`AccordionEditorContext` state, entirely unrelated to and unaffected by the trigger-content-model change in this spec.
- **`motto/accordion`'s own `templateLock` is `false`**, not `"all"` like `motto/tabs`. It was already immune to the SDD-022 remount-deletion bug before this spec; the *new* `templateLock: "all"` surface this spec introduces is one level deeper (`accordion-item`'s own trigger/panel split), not at the `accordion` level.
- **A fixed, non-optional chevron icon** (`ChevronDown`) exists on every trigger, separate from the optional custom icon — tabs has no equivalent "always-present icon" concept. It stays a plain sibling render in `accordion-trigger`, not part of the `InnerBlocks` content.
- **Richer existing ARIA wiring** (`aria-expanded`/`aria-controls`/`aria-labelledby`/`role="region"`) that tabs never had — this spec must preserve it exactly, now split across two blocks reading shared `itemId`/`isOpen` context instead of one block computing everything locally.
- **No numbered default text preserved on insert.** Tabs' default template could pass `{ tabId: "tab-1", label: "Tab 1" }`-style distinct attributes per slot because `motto/tabs` itself seeds its children's *content* directly (own effect, own `createBlock` calls). Here, `motto/accordion`'s template only creates 2 plain `accordion-item`s (no content-seeding effect exists at that level, and adding one would duplicate `accordion-item`'s own seed effect) — both default to the generic "Accordion item" text from `accordion-item`'s own seed effect. Confirmed acceptable with the user before implementation (matches how a manually-appended `tab-button` also defaults to generic "Tab", not a numbered label).

### 4.7 Discovered during implementation: `save()` has no access to block context
The original draft (§4.1/§4.2 as first written) planned for `accordion-trigger`/`accordion-panel` to rely purely on `usesContext` for `itemId`/`isOpen`, with no attributes of their own. This doesn't work: WordPress `save()` functions only ever receive `{ attributes }` — block context (`usesContext`/`providesContext`) is an editor-time-only React mechanism (`BlockContext.Provider`), never available at save/serialization time. Since both new blocks need `itemId` (for `id`/`aria-controls`/`aria-labelledby`) and `isOpen` (for `aria-expanded`/`aria-hidden`) in their own static frontend markup, they each declare their own duplicated `itemId`/`isOpen` **attributes** too — exactly the same pattern `motto/tabs` already uses for `tabId` on both `tab-button` and `tab`. `accordion-item`'s own seed/sync effect (§4.3) is the single place that keeps these duplicated copies correct, pushed one-way, on every relevant change.

### 4.8 Follow-up: real production content required a `deprecated`/`migrate()` entry after all
Discovered after shipping v0.2: `housing-hub` (a live client site) had a published page (`Community Housing Providers`, `wp:motto/accordion-item` blocks with `label`/`customIcon`/`iconOptions` set on some items — rich text labels like `"1 <strong>Land or property</strong>"`, one item with a custom icon) that broke — every `accordion-item` showed as an invalid block with a "Attempt Block Recovery" prompt — the instant this spec's `block.json` attribute changes went live there. Confirmed via the WP REST API (`?context=edit`, `content.raw`) that the underlying `post_content` was completely untouched (nothing was actually lost at the data layer); the frontend kept rendering perfectly throughout, since static blocks just re-emit whatever HTML is stored, regardless of the currently-registered block shape. The failure was purely an editor-side re-parse mismatch.

Added a single `deprecated` array entry to `motto/accordion-item`:
- **`attributes`**: the exact pre-SDD-024 schema (`itemId`, `label`, `isOpen`, `customIcon`, `iconPosition`, `iconOptions`), copied from the last-committed `block.json` (`git show HEAD:...`) rather than from memory, to guarantee byte-for-byte accuracy.
- **`save()`**: the exact pre-SDD-024 `Save()` function body, copied the same way — this is what WordPress's block validator compares old saved HTML against to decide whether this deprecated entry matches.
- **`migrate(attributes, innerBlocks)`**: builds the new `{ itemId, isOpen }` attribute pair, and two new child blocks — `motto/accordion-trigger` seeded with `createBlock("core/paragraph", { content: label })` (the old `label` string — itself already an HTML string, e.g. containing `<strong>`, since the old attribute had no `source`/`selector` and `RichText` serializes formatted content as raw HTML — passes straight into `core/paragraph`'s own HTML-string `content` attribute with formatting intact, no conversion needed) plus, if `customIcon` was true, a `motto/svg` block built by a new small `buildSvgAssetFromLegacyIconOptions()` helper that maps the old button-icon shape (`{type: "none"|"image"|"svg", image, svg}`) onto `motto/svg`'s own `svgAsset` shape (`{source: "lucide"|"media"|"inline", media, svg}`), ordered before/after the text paragraph per the old `iconPosition` — and `motto/accordion-panel` wrapping the untouched original `innerBlocks` (the panel content was already real nested blocks, needing no attribute translation, just a new wrapper).

**A second, more important bug found via this exercise**: while verifying the migration path with a *synthetic* (hand-typed) legacy post, a subtle JSON-escaping mistake in the test data caused the deprecated `save()` match to fail — and in that failure mode, `accordion-item`'s own seed effect (§4.3) silently **replaced the real (unmigrated) panel content with blank defaults**, with no invalid-block warning shown at all, because WordPress's parser had already salvaged the shared `itemId`/`isOpen` keys against the *current* attribute schema (both old and new schemas happen to share those two names) and considered the block "valid enough" to mount normally — it just never restructured the children into trigger/panel. The seed effect's original guard, `if (!triggerBlock && !panelBlock)`, doesn't distinguish "genuinely empty" from "has real children that just aren't named right" — it treated both the same and overwrote either. **Fixed** by tightening the guard to `if (directChildren.length === 0)`: seeding now only ever fires when the item has zero children of any kind, never when unexpected content is present. This is strictly safer (a subset of the old condition) and confirmed not to regress any of the 6 existing e2e tests. The real `housing-hub` migration itself was unaffected by this bug (its deprecated `save()` matched cleanly, `migrate()` ran correctly) — but the same failure mode could plausibly hit some other not-yet-seen production edge case, so the guard was tightened regardless, as cheap insurance.

Verified end-to-end against the real affected content (not just the synthetic repro): fetched the page's rendered HTML before and after the fix shipped, and diffed every `<p>`/`<li>` text node between the two snapshots — 0 lost, 48/48 matched, plus the 5 trigger labels themselves (previously in a `<span>`, now correctly inside each trigger's `<p>`) confirmed present with formatting (`<strong>`) intact.

## 5. Data Contract
- `motto/accordion-item` attributes shrink to `{ itemId, isOpen }` — `label`/`customIcon`/`iconOptions`/`iconPosition` removed.
- `motto/accordion-trigger` (new): `{ itemId, isOpen }` — duplicated copies of the parent's own values (§4.7), needed for `save()`; content otherwise lives entirely in `InnerBlocks`.
- `motto/accordion-panel` (new): `{ itemId, isOpen }` — same reason.
- New block context: `motto/accordion-item-itemId` (string), `motto/accordion-item-isOpen` (boolean), provided by `accordion-item`, consumed by both new children's `edit()` for live reactivity (their own duplicated attributes are used only in `save()`).
- Persistence: `accordion-item` persists a fixed 2-child structure (`accordion-trigger`, `accordion-panel`); `accordion-trigger` persists real `InnerBlocks` (`core/paragraph` + optional `motto/svg`) instead of attribute-driven trigger markup.
- Outputs: DOM structure for `accordion-frontend.js`'s `:scope >` queries is unchanged — `.motto-accordion-item > .motto-accordion-item__trigger` and `.motto-accordion-item > .motto-accordion-item__panel > .motto-accordion-item__panel-inner` still hold, now each rendered by a distinct block's own root instead of one block's inline markup. Verified live: `accordion-frontend.js`'s click-toggle and `aria-expanded`/`.is-open`/height-animation all work unchanged against the new split DOM.

## 7. Risks and Mitigations
- Risk: reintroducing the exact SDD-022 §4.5 regression at the new `accordion-item` `templateLock: "all"` layer, if a future edit adds nested content to the trigger/panel template entries.
  - Mitigation: designed shallow from the start (§4.3), documented in code comments and this spec; the new "3rd item survives publish + reopen" e2e test (§6, §8) guards against it directly.
- Risk: the toggle-click logic, relocated from `accordion-item` to `accordion-trigger`, subtly changes behavior in an edge case not covered by the 3-branch description in §Current Behavior (e.g. list-view/keyboard-driven selection interactions, which `motto/tab-button` handles via a dedicated `isSelected`-driven `useEffect` that `accordion-item` never had).
  - Mitigation: port the logic verbatim first; only add a `tab-button`-style selection-sync effect if manual/e2e testing surfaces a real gap, not preemptively.
- Risk: `TabTriggerContent`/`TabTriggerEditor` (`tab-trigger-content.jsx`) becomes fully dead code once `accordion-item` stops using it (its last consumer, per §3) — leaving unused exports behind if not flagged.
  - Mitigation: explicitly noted as an out-of-scope cleanup candidate (§Current Behavior); not deleted in this pass to keep this spec's diff focused.
- Risk: losing the distinct "Item 1"/"Item 2" default text on fresh accordion insert (§4.6) may be an unwanted regression in practice, not just a documented tradeoff.
  - Mitigation: flagged explicitly for user confirmation before implementation; cheap to add a parallel seed effect in `motto/accordion` if wanted.
- ~~Risk: block family confirmed unused in production~~ — **this materialized**: real content on `housing-hub` broke on ship. Resolved via the §4.8 `deprecated`/`migrate()` follow-up, verified against the actual affected content with zero data loss (nothing was ever lost at the storage layer to begin with — this was purely an editor re-parse break).
